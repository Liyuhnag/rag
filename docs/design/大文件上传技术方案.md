## 1. 概述

### 1.1 背景

随着文档规模增长，单文件达到 1GB 级。原有整文件读取、单请求上传的方式在内存占用、传输进度、失败恢复和并发能力上无法满足要求。

本方案采用 S3 Multipart Upload，将文件切分为固定大小的分片，由上传服务代理写入对象存储，实现大文件分片传输、断点续传、失败重试和异步处理。

### 1.2 目标

- 支持单文件上限约 1000MiB；
- 支持约 10 人同时上传；
- 使用 8MiB 固定分片，由 S3 完成最终合并；
- 支持暂停、失败重试、刷新页面后重新选择同一文件继续上传；
- 上传服务不保存完整文件，不占用与文件大小线性相关的内存；
- 上传完成后异步触发文档解析流程；
- 支持上传进度、任务进度和异常状态的可观测。

### 1.3 适用范围

本方案覆盖从浏览器选择文件到上传完成、写入文档记录并投递解析任务的完整链路，适用于上传 API、对象存储适配层、任务创建与投递、前端上传队列。

文档解析、切块、向量化和索引属于下游处理流程，按各自设计执行。

### 1.4 术语

| 术语 | 说明 |
| --- | --- |
| Multipart Upload | S3 分片上传协议，由对象存储将多个分片合并为单个对象。 |
| Part | Multipart Upload 中的一个分片，编号从 1 开始。 |
| ETag | 对象存储返回的分片实体标识；完成上传时用于提交分片清单。 |
| ListParts | S3 接口，列出某个 Multipart Upload 已上传的分片。 |
| upload_id | 上传会话标识，32 位十六进制字符串。 |
| document_id | 文档标识，32 位十六进制字符串，在上传初始化阶段生成。 |
| task_id | 文档处理任务标识，32 位十六进制字符串。 |
| fingerprint | 全文件 SHA-256，64 位小写十六进制，用于匹配续传会话。 |
| 上传会话 | 一次文件上传的完整生命周期，对应一个 Multipart Upload。 |

### 1.5 设计约束

| 项目 | 约束 |
| --- | --- |
| 单文件上限 | 1000MiB（1,048,576,000 字节） |
| 分片大小 | 8MiB（8,388,608 字节） |
| 并发规模 | 约 10 个上传用户 |
| 网络环境 | 内网 |
| 对象存储 | SeaweedFS 3.99，S3 兼容接口 |
| 数据库 | MySQL 8.0 |
| 队列 | Redis 7 + Celery 5.6 |
| 后端 | Python 3.12 + FastAPI + boto3 |
| 前端 | Vue 3 + Vite |
| 部署形态 | API 与 S3 分离部署，通过内网访问；代码不依赖同机部署 |
| 浏览器访问范围 | 上传链路中浏览器只访问 API；文件下载/预览通过文件访问服务 |

## 2. 总体设计

### 2.1 系统架构

```text
┌──────────────┐
│   浏览器      │
│ 分片 / 进度   │
└──────┬───────┘
       │ HTTP：init / part / status / complete / abort
       ▼
┌────────────────────────┐        ┌──────────────────────────┐
│   FastAPI 上传服务      │───────▶│  SeaweedFS S3            │
│   - 会话创建与复用      │        │  - Multipart Upload      │
│   - 分片校验与转发      │        │  - 分片存储与合并         │
│   - 完成合并与落库      │        └──────────────────────────┘
│   - 任务投递            │
└──────┬─────────────────┘
       │
       ├──▶ MySQL：upload_sessions / documents / document_tasks
       │
       └──▶ Redis / Celery：解析任务队列
                 │
                 ▼
           ┌──────────────┐
           │  解析 Worker  │
           └──────────────┘
```

### 2.2 组件职责

| 组件 | 职责 |
| --- | --- |
| 浏览器 | 计算文件指纹、切片、调用上传 API、展示真实进度、暂停/恢复、刷新后续传。 |
| 上传服务 | 创建/复用会话、校验参数、缓冲并转发分片、完成合并、写入文档与任务、投递解析任务。 |
| SeaweedFS S3 | 保存分片、合并对象、提供 `ListParts` 分片状态。 |
| MySQL | 保存上传会话、文档元数据、处理任务、版本和进度。 |
| Redis / Celery | 承载解析任务队列、任务补投和后续运维任务。 |
| 解析 Worker | 消费解析任务，更新文档和任务状态；解析细节由下游设计定义。 |

### 2.3 核心流程

1. 浏览器计算全文件 SHA-256，调用 `POST /api/uploads/init`；
2. 上传服务创建或复用上传会话，并在 S3 创建 Multipart Upload；
3. 浏览器按 8MiB 切片，逐片调用 `PUT /api/uploads/{uploadId}/parts/{partNumber}`；
4. 上传服务校验会话、分片号和大小，将分片转发到 S3；
5. 浏览器调用 `POST /api/uploads/{uploadId}/complete`；
6. 上传服务通过 `ListParts` 校验分片完整性，调用 `CompleteMultipartUpload` 合并；
7. 上传服务在数据库事务中写入 `documents`、`document_tasks`，并将会话置为 `COMPLETED`；
8. 事务提交后投递解析任务；解析任务进入异步队列；
9. 浏览器轮询 `GET /api/tasks/{taskId}` 展示解析进度。

### 2.4 设计原则

- **分片状态以 S3 为准**：已上传分片通过 `ListParts` 查询，不使用 Redis bitmap 或本地文件维护第二套状态。
- **业务状态以 MySQL 为准**：上传会话、文档、任务和版本全部持久化在 MySQL。
- **单分片缓冲**：上传服务在同一时刻只持有一个分片大小的缓冲，不保存完整文件。
- **状态机驱动**：`complete`、`abort`、过期清理都通过数据库条件更新抢占状态，保证并发安全。
- **幂等优先**：重复初始化、重复分片、重复完成、重复取消均按幂等处理。
- **异步解耦**：上传完成与文档解析解耦，解析任务通过 `PENDING` 状态和补投机制保证最终执行。

## 3. 上传流程

### 3.1 初始化

#### 3.1.1 请求参数

```json
{
  "filename": "年度报告.pdf",
  "sizeBytes": 1048576000,
  "fingerprint": "9f2c...64位小写十六进制"
}
```

- 文件类型由服务端根据文件名扩展名推导，不使用客户端传入的类型；
- 分片大小由服务端配置固定为 8MiB，不接受客户端指定；
- `sizeBytes` 必须大于 0 且不超过单文件上限；
- `fingerprint` 必须是 64 位小写十六进制。

#### 3.1.2 会话复用规则

| 条件 | 处理 |
| --- | --- |
| 存在同指纹、`UPLOADING`、未过期，且文件名和大小一致 | 复用会话，调用 `ListParts` 返回已上传分片，`200` |
| 存在同指纹、`UPLOADING`、未过期，但文件名或大小不一致 | 返回 `409 FINGERPRINT_CONFLICT` |
| 存在同指纹的过期 `UPLOADING` | 标记为 `ABORTING(EXPIRED)`，创建新会话 |
| 存在同指纹的 `COMPLETING` | 返回 `202`，响应中带 `uploadId` 和 `status` |
| 存在同指纹的 `COMPLETED`，且对应文档仍存在 | 返回 `200`，带已有 `documentId`、`taskId`、`taskStatus` |
| 存在同指纹的 `ABORTING` | 返回 `202`，提示正在取消 |
| 其他终态或无会话 | 创建新会话，返回 `201` |

#### 3.1.3 新会话创建

- 生成 `upload_id` 和 `document_id`；
- 对象键为 `documents/{document_id}/source/{filename}`；
- 调用 S3 `CreateMultipartUpload`；
- 写入 `upload_sessions`，状态为 `UPLOADING`；
- 计算 `totalParts = ceil(sizeBytes / chunkSize)`，最多 10000 片；
- 设置 `expires_at = now + 24h`。

#### 3.1.4 并发初始化

同一个指纹最多存在一个 `UPLOADING` 或 `COMPLETING` 会话，通过生成列和唯一索引保证：

```sql
active_fingerprint CHAR(64) GENERATED ALWAYS AS (
    CASE
        WHEN status IN ('UPLOADING', 'COMPLETING') THEN fingerprint
        ELSE NULL
    END
) STORED,
UNIQUE KEY uk_upload_sessions_active_fingerprint (active_fingerprint)
```

并发初始化处理顺序：

1. 查询活跃会话，存在则复用；
2. 不存在则创建 S3 Multipart Upload；
3. 插入会话记录；
4. 若唯一索引冲突，取消本次新建的 Multipart Upload，重新查询成功创建的会话并返回；
5. 其他写入失败时，取消本次 Multipart Upload，返回存储或数据库错误。

### 3.2 分片上传

```http
PUT /api/uploads/{uploadId}/parts/{partNumber}
Content-Type: application/octet-stream
Content-Length: 8388608
```

请求体为分片原始字节。服务端处理：

1. 校验会话存在且为 `UPLOADING`，未过期；
2. 校验 `partNumber` 在 `1..totalParts` 范围内；
3. 校验 `Content-Length`：
   - 缺失返回 `411 LENGTH_REQUIRED`；
   - 超过预期返回 `413 PART_TOO_LARGE`；
   - 不等于预期返回 `422 INVALID_PART_SIZE`；
4. 获取并发槽位后读取请求体，再次核对实际字节数；
5. 调用 S3 `UploadPart`；
6. 返回 `{partNumber, sizeBytes}`，不写 MySQL，不返回 ETag。

非最后一片大小必须等于 `chunkSize`；最后一片大小等于：

```text
sizeBytes - (totalParts - 1) * chunkSize
```

同一分片号重复上传直接覆盖 S3 同编号分片，天然幂等。

### 3.3 查询上传状态

```http
GET /api/uploads/{uploadId}
```

返回会话元数据、状态和已上传分片：

```json
{
  "uploadId": "0f3a...",
  "documentId": "a1b2...",
  "filename": "年度报告.pdf",
  "sizeBytes": 1048576000,
  "chunkSize": 8388608,
  "totalParts": 125,
  "status": "UPLOADING",
  "uploadedParts": [
    {"partNumber": 1, "sizeBytes": 8388608}
  ],
  "expiresAt": "2026-10-21T12:00:00Z",
  "errorMessage": null
}
```

终态处理：

- `COMPLETED`：`uploadedParts` 返回空数组，附带 `taskId`、`taskStatus`；
- `ABORTED`、`EXPIRED`、`FAILED`：`uploadedParts` 返回空数组，`errorMessage` 有值时返回；
- `COMPLETING`：Multipart Upload 仍存在时返回已上传分片，已合并时返回空数组；
- 会话不存在返回 `404 UPLOAD_NOT_FOUND`。

### 3.4 完成上传

```http
POST /api/uploads/{uploadId}/complete
```

处理顺序：

1. 条件更新会话为 `COMPLETING`，递增 `claim_version`，记录 `updated_at`；
2. `ListParts` 校验 `1..totalParts` 全部存在且大小正确；
3. 调用 `CompleteMultipartUpload`，提交按分片号升序排列的分片清单；
4. 在数据库事务中写入 `documents`、`document_tasks(version=1)`，并将会话置为 `COMPLETED`；
5. 事务提交后投递解析任务；
6. 返回会话和任务状态。

响应示例：

```json
{
  "uploadId": "0f3a...",
  "documentId": "a1b2...",
  "status": "COMPLETED",
  "taskId": "c3d4...",
  "taskStatus": "PENDING"
}
```

缺分片时返回 `409 UPLOAD_INCOMPLETE`，`details.missingParts` 给出缺失编号。

### 3.5 取消上传

```http
DELETE /api/uploads/{uploadId}
```

- 条件更新 `UPLOADING` 为 `ABORTING`，记录取消原因为 `USER`；
- 调用 `AbortMultipartUpload`；
- 成功后置为 `ABORTED`；
- 已完成返回 `409 UPLOAD_ALREADY_COMPLETED`；
- 正在完成返回 `409 UPLOAD_COMPLETING`；
- 已取消或已过期幂等返回 `204`。

### 3.6 断点续传

#### 3.6.1 文件指纹

浏览器使用流式 SHA-256 计算全文件指纹，在 Web Worker 中执行，不阻塞页面。指纹只计算结果文件的字节内容，不包含文件名、大小和修改时间。

`init` 复用会话时同时校验 `filename` 和 `sizeBytes`，避免不同文件复用同一会话。

#### 3.6.2 本地记录

浏览器在 `localStorage` 的 `rag.upload.v2` 中保存任务元数据：

```json
[
  {
    "fingerprint": "9f2c...",
    "uploadId": "0f3a...",
    "filename": "年度报告.pdf",
    "sizeBytes": 1048576000,
    "lastModified": 1760000000000,
    "createdAt": "2026-10-20T08:00:00Z",
    "updatedAt": "2026-10-20T08:10:00Z"
  }
]
```

只保存元数据，不保存分片列表和 ETag。多标签页通过 `storage` 事件同步。

#### 3.6.3 刷新后的恢复

1. 页面加载时读取 `rag.upload.v2`；
2. 对每条记录调用 `GET /api/uploads/{uploadId}`；
3. `UPLOADING` 显示“待继续上传”；`COMPLETING` 显示“正在处理”；`COMPLETED` 显示已完成；`ABORTED`、`EXPIRED`、`404` 移除记录；网络错误保留记录；
4. 用户重新选择同一文件后，浏览器重新计算指纹并调用 `init`；
5. 服务端返回 `uploadedParts`，浏览器只上传缺失分片；
6. 上传完成或取消后清理本地记录。

本地记录被清空不影响续传正确性：重新选择文件后仍可通过指纹匹配未过期会话。

### 3.7 会话有效期

- 新建会话有效期 24 小时；
- 每次成功复用 `UPLOADING` 会话时，将 `expires_at` 续期到当前时间加 24 小时；
- 状态查询不续期；
- 过期会话由清理任务或下一次初始化迁移到 `ABORTING(EXPIRED)`，随后取消 Multipart Upload 并置为 `EXPIRED`。

## 4. 会话状态机

### 4.1 状态定义

| 状态 | 含义 | 允许操作 | 终态 |
| --- | --- | --- | --- |
| `UPLOADING` | 正常接收分片 | 上传分片、完成、取消 | 否 |
| `COMPLETING` | 已抢占完成流程，正在校验、合并、写库 | 查询、幂等完成 | 否 |
| `COMPLETED` | 合并并落库成功 | 幂等返回 | 是 |
| `ABORTING` | 已抢占取消或过期清理，正在取消 Multipart Upload | 查询、重试取消 | 否 |
| `ABORTED` | 用户主动取消完成 | — | 是 |
| `EXPIRED` | 过期清理完成 | — | 是 |
| `FAILED` | 不可恢复，需要重新上传 | — | 是 |

### 4.2 状态迁移

```text
init
  └──> UPLOADING

UPLOADING --完成抢占--> COMPLETING
COMPLETING --成功--> COMPLETED
COMPLETING --可恢复失败（确认 S3 未合并）--> UPLOADING
COMPLETING --不可恢复失败--> FAILED

UPLOADING --取消抢占（USER）--> ABORTING
UPLOADING --过期抢占（EXPIRED）--> ABORTING
ABORTING --取消成功（USER）--> ABORTED
ABORTING --取消成功（EXPIRED）--> EXPIRED

COMPLETING / ABORTING --租约过期--> 允许接管
```

### 4.3 并发控制

所有状态迁移使用 MySQL 条件更新，依赖单行原子性，不引入 Redis 状态锁。

完成抢占示例：

```sql
UPDATE upload_sessions
SET status = 'COMPLETING',
    claim_version = claim_version + 1,
    updated_at = UTC_TIMESTAMP(6)
WHERE id = ?
  AND status = 'UPLOADING'
  AND expires_at > UTC_TIMESTAMP(6)
```

- 影响 1 行表示抢占成功；
- 影响 0 行表示状态已变化，按当前状态返回幂等结果或错误；
- `claim_version` 用于接管 fencing：最终写库时带 `status='COMPLETING' AND claim_version=?`，不匹配则回滚，避免旧执行者双写。

`COMPLETING` 和 `ABORTING` 使用 `updated_at` 作为租约，默认 5 分钟。租约过期后允许其他请求条件接管。

### 4.4 异常恢复

#### 4.4.1 S3 已合并、数据库写入失败

- 会话保持 `COMPLETING`，不回退 `UPLOADING`；
- 接管时先调用 `HeadObject(object_key)`：
  - 对象存在且大小等于 `sizeBytes`：跳过合并，补写 `documents` 和 `document_tasks`；
  - 对象不存在：重新 `ListParts` 并调用 `CompleteMultipartUpload`；
  - Multipart Upload 不存在且对象也不存在：置为 `FAILED`；
  - S3 暂时不可用：保持 `COMPLETING`，返回可重试错误。

#### 4.4.2 完成与分片并发

- 前端在调用 `complete` 前必须等待所有分片请求结束；
- 服务端在 `CompleteMultipartUpload` 收到 `InvalidPart` 时，重新 `ListParts` 后重试一次；
- 仍失败则回退 `UPLOADING`，允许客户端补传后重试；
- `COMPLETING` 状态下分片接口直接拒绝。

#### 4.4.3 重复完成

- `COMPLETED` 幂等返回已有文档和任务；
- `COMPLETING` 租约有效时返回进行中；
- 租约过期后才允许接管。

## 5. 数据模型

### 5.1 实体关系

```text
upload_sessions 1 ─── 1 documents
documents       1 ─── N document_tasks
```

- `upload_sessions.document_id` 唯一；
- `document_tasks.document_id + version` 唯一；
- 重新解析时 `document_id` 不变，`version` 递增。

### 5.2 `upload_sessions`

```sql
CREATE TABLE IF NOT EXISTS upload_sessions (
    id VARCHAR(32) NOT NULL COMMENT '上传会话 ID（upload_id）',
    document_id VARCHAR(32) NOT NULL COMMENT '预生成的文档 ID',
    fingerprint CHAR(64) CHARACTER SET ascii COLLATE ascii_bin NOT NULL
        COMMENT '全文件 SHA-256',
    active_fingerprint CHAR(64) CHARACTER SET ascii COLLATE ascii_bin
        GENERATED ALWAYS AS (
            CASE
                WHEN status IN ('UPLOADING', 'COMPLETING') THEN fingerprint
                ELSE NULL
            END
        ) STORED COMMENT '活跃会话指纹，非活跃为 NULL',
    filename VARCHAR(255) NOT NULL COMMENT '规范化后的文件名',
    file_type VARCHAR(32) NOT NULL COMMENT '扩展名',
    size_bytes BIGINT NOT NULL COMMENT '文件总字节数',
    chunk_size INT NOT NULL COMMENT '分片大小，固定 8388608',
    total_parts INT NOT NULL COMMENT '分片总数',
    object_key VARCHAR(1024) NOT NULL COMMENT '最终对象 key',
    s3_upload_id VARCHAR(1024) NOT NULL COMMENT 'S3 Multipart Upload ID',
    status VARCHAR(32) NOT NULL
        COMMENT 'UPLOADING/COMPLETING/COMPLETED/ABORTING/ABORTED/EXPIRED/FAILED',
    abort_reason VARCHAR(16) NULL COMMENT 'USER/EXPIRED',
    claim_version INT NOT NULL DEFAULT 0 COMMENT '接管 fencing',
    error_message VARCHAR(1024) NULL COMMENT '失败原因',
```

### 5.6 数据约定

- 时间统一使用 UTC，字段类型为 `DATETIME(6)`，比较使用数据库时间；
- 主键统一为 32 位十六进制字符串；
- `fingerprint` 和 `source_sha256` 使用 ascii 字符集，避免索引膨胀；
- 不使用外键，关系由服务层保证；
- `documents.chunk_count` 表示子块数量，`parent_chunk_count` 表示父块数量；
- `upload_sessions.document_id` 唯一；
- `document_tasks (document_id, version)` 唯一；
- 对象键和文件 URL 除字符长度外，还需校验 UTF-8 字节数不超过 S3 键上限 1024 字节；
- `file_url` 指向文件访问服务，不直接暴露 S3 接口；
- 如数据库未安装 ngram 插件，可移除 `documents` 的全文索引。

## 6. 接口规范

### 6.1 通用约定

- 基础路径：`/api`；
- HTTP JSON 字段使用 camelCase，数据库和 Python 内部字段使用 snake_case；
- 时间使用 ISO 8601 UTC，带 `Z`，如 `2026-10-21T12:00:00Z`；
- ID 为 32 位十六进制字符串；
- 状态枚举大写；
- 错误响应统一格式：

```json
{
  "error": {
    "code": "INVALID_PART_SIZE",
    "message": "分片大小与预期不符",
    "details": {
      "expected": 8388608,
      "actual": 123
    }
  }
}
```

- 单文件上限由 `MAX_DOCUMENT_BYTES` 配置，默认 1,048,576,000 字节；
- 分片接口使用 `application/octet-stream`，其余接口使用 `application/json`。

### 6.2 初始化上传

```http

```

请求：

```json
}
```

复用成功 `200`：字段相同，`uploadedParts` 为已上传分片：


已完成 `200`：

```json

  "uploadId": "0f3a...",
  "documentId": "a1b2...",
  "status": "COMPLETED",
  "chunkSize": 8388608,

}
```

进行中 `202`：

```json

  "documentId": "a1b2...",

  "expiresAt": "2026-10-21T12:00:00Z"
}
```

`ABORTING` 状态同样返回 `202`。

### 6.3 上传分片

```http
PUT /api/uploads/{uploadId}/parts/{partNumber}
Content-Type: application/octet-stream
Content-Length: 8388608
```

成功 `200`：

```json
{
  "partNumber": 1,
  "sizeBytes": 8388608
}
```

规则：

- `partNumber` 从 1 开始，最大 `totalParts`；
- 非最后一片必须等于 `chunkSize`，最后一片按剩余大小；
- `Content-Length` 必须存在；
- 超过预期返回 `413 PART_TOO_LARGE`；
- 不等于预期返回 `422 INVALID_PART_SIZE`；
- 读取请求体时二次核对实际字节数；
- 同一分片重复上传覆盖 S3 同编号分片；
- 不返回 ETag，完成时由服务端通过 `ListParts` 获取。

### 6.4 查询上传状态

```http
GET /api/uploads/{uploadId}
```

`200`：

```json

  "documentId": "a1b2...",

  "chunkSize": 8388608,
  "totalParts": 125,
```

## 7. 可靠性与补偿

### 7.1 完成事务

完成上传在同一个数据库事务中执行：

1. 插入 `documents`；
2. 插入 `document_tasks`，`version=1`，状态 `PENDING`；
3. 更新 `upload_sessions` 为 `COMPLETED`。

事务提交后再投递解析任务。外部副作用不放在事务内，避免事务回滚后消息已投递。

### 7.2 任务投递补偿

解析任务投递失败时：

- 任务保持 `PENDING`，接口仍返回 `200`；
- 不回滚事务、不标记 `FAILED`；
- 记录日志和指标。

`document_tasks` 中的 `PENDING` 记录作为待投递消息。补投任务每 5 分钟执行一次：

```text
SELECT document_tasks
WHERE status = 'PENDING'
  AND updated_at < now() - 5 分钟
ORDER BY created_at
LIMIT 50
FOR UPDATE SKIP LOCKED
```

逐个投递，投递后更新 `updated_at`。重复消息由 Worker 幂等处理。

Worker 入口使用条件更新抢占任务：

```sql
UPDATE document_tasks
SET status = 'RUNNING',
    stage = 'SPLITTING',
    progress = 0,
    updated_at = UTC_TIMESTAMP(6)
WHERE id = ?
  AND status = 'PENDING'
```

影响 1 行表示抢占成功；影响 0 行表示任务已被其他 Worker 取走或已进入终态。

### 7.3 清理任务

| 任务 | 频率 | 扫描条件 | 动作 |
| --- | --- | --- | --- |
| `expire_uploads` | 每小时 | `UPLOADING` 且 `expires_at <= now()` | 置 `ABORTING(EXPIRED)`，取消 Multipart Upload，置 `EXPIRED` |
| `retry_aborting` | 每小时 | `ABORTING` 且租约过期 | 重试取消，置 `ABORTED` 或 `EXPIRED` |
| `recover_completing` | 每 5 分钟 | `COMPLETING` 且租约过期 | 按恢复流程处理 |
| `cleanup_orphan_mpu` | 每天 | 无对应会话的 Multipart Upload | 超过宽限期后取消 |
| `cleanup_orphan_object` | 每天 | `FAILED`/`ABORTED`/`EXPIRED` 超过 7 天，对象存在但无文档记录 | 删除对象 |
| `redispatch_pending_tasks` | 每 5 分钟 | `PENDING` 且超过 5 分钟 | 重新投递解析任务 |
| `cleanup_old_sessions` | 每天 | 终态且超过 30 天 | 删除会话记录 |

#### 7.3.1 完成恢复

`COMPLETING` 超时后先走恢复，不直接取消：

1. `HeadObject(object_key)`；
2. 对象存在且大小正确：补写 `documents` 和 `document_tasks`，置 `COMPLETED`；
3. 对象不存在：`ListParts`；
4. 分片齐全：调用 `CompleteMultipartUpload`，再补写数据库；
5. 分片缺失且会话未过期：回退 `UPLOADING`，允许补传；
6. 分片缺失且会话已过期：置 `ABORTING(EXPIRED)`；
7. Multipart Upload 不存在且对象不存在：置 `FAILED`；
8. S3 暂时不可用：保持 `COMPLETING`，下一轮重试。

#### 7.3.2 孤儿 Multipart Upload

正常流程先创建 Multipart Upload，再插入会话记录；若插入前进程退出，会留下无会话的 Multipart Upload。

- 使用 `ListMultipartUploads` 列出进行中的 Multipart Upload；
- 按 `s3_upload_id` 查询会话；
- 无对应会话、或会话已终态且超过 24 小时宽限期：取消 Multipart Upload；
- 仅处理创建时间超过 1 小时的对象，避免与正在初始化的请求冲突。

该清理依赖 SeaweedFS 的 `ListMultipartUploads` 接口，部署前需确认接口可用。

#### 7.3.3 孤儿对象

S3 已合并、数据库长期写入失败并最终变成 `FAILED` 时，会留下无文档记录的对象。

- 只扫描 `FAILED`、`ABORTED`、`EXPIRED` 且超过 7 天的会话；
- `HeadObject` 判断对象是否存在；
- 对象存在且 `documents` 无对应 `document_id`：删除对象；
- 对象存在但 `documents` 有记录：不删除，记录告警。

#### 7.3.4 执行原则

- 先条件更新抢占状态，再调用 S3，不在数据库事务中等待 S3；
- 批量扫描使用 `FOR UPDATE SKIP LOCKED`，每批 50–100 条；
- 取消和删除忽略 `NoSuchUpload`、`NoSuchKey`；
- 终态更新带条件，避免与用户请求互相覆盖；
- 清理任务运行在独立 `maintenance` 队列，并发 1；
- Celery beat 必须部署；无 beat 时使用系统定时任务调用同一管理命令。

### 7.4 监控指标

| 指标 | 说明 |
| --- | --- |
| `upload_inflight_parts` | 当前在途分片数 |
| `upload_waiting_parts` | 等待槽位的请求数 |
| `upload_part_duration` | 分片上传耗时 |
| `upload_429_total` | `UPLOAD_BUSY` 次数 |
| `upload_pending_task_age` | `PENDING` 任务最大年龄 |
| `upload_completing_age` | `COMPLETING` 状态持续时间 |
| `upload_orphan_mpu` | 孤儿 Multipart Upload 数量 |
| `upload_orphan_object` | 孤儿对象数量 |
| `upload_abort_failure` | 取消失败次数 |

告警建议：

- `PENDING` 任务超过 15 分钟；
- `COMPLETING` 超过 10 分钟；
- 取消失败连续出现；
- 等待分片数长期接近上限；
- API 内存接近预算；
- boto3 连接池耗尽。

## 8. 并发与容量

### 8.1 并发预算

按 10 个用户、每文件 2 个分片并发：

- 在途分片：10 × 2 = 20；
- 内存：20 × 8MiB = 160MiB；
- 加上请求解析、boto3 缓冲和其他运行时开销，按 256MiB 预算；
- API 主要等待网络，CPU 压力较低。

### 8.2 限流参数

| 项 | 值 | 说明 |
| --- | --- | --- |
| API 进程数 | 1 | 单实例部署，I/O 密集型 |
| 全局在途分片 | 20 | 进程内 `asyncio.Semaphore` |
| 每文件并发分片 | 2 | 前端限制 |
| 等待队列上限 | 40 | 超过直接返回 429 |
| 最长等待 | 30 秒 | 超时返回 `429 UPLOAD_BUSY` |
| FastAPI 线程池 | 40 | 大于在途分片数，留出其他接口余量 |
| boto3 连接池 | 50 | `max_pool_connections=50` |
| boto3 连接超时 | 10 秒 | |
| boto3 读取超时 | 120 秒 | 与单分片超时对齐 |
| nginx 请求体上限 | 9m | 8MiB 分片留余量 |
| uvicorn 并发上限 | 200 | 大于分片数和状态查询量 |

### 8.3 服务端实现

- 分片接口使用 `async def`，先获取 `asyncio.Semaphore(20)` 槽位，再读取请求体；
- 等待槽位使用 `asyncio.wait_for`，超时 30 秒；
- 等待中的请求不占用线程池；
- 读取 8MiB 后，通过 `run_in_threadpool` 调用 boto3 `upload_part`；
- 槽位在 `finally` 中释放；
- 进程内维护等待计数，超过 40 直接拒绝；
- 429 响应携带 `Retry-After: 5`。

分片接口不得使用同步 `def` 阻塞等待信号量，否则等待请求会占满线程池，影响初始化、状态查询和完成接口。

### 8.4 部署参数

- nginx：
  - `client_max_body_size 9m`；
  - `proxy_request_buffering off`；
  - `proxy_read_timeout 120s`；
  - `client_body_timeout 120s`；
- uvicorn：`--workers 1 --limit-concurrency 200`；
- FastAPI 线程池：40；
- boto3：`max_pool_connections=50`、`connect_timeout=10`、`read_timeout=120`、`retries=3`；
- MySQL：按 20 个并发分片各一次会话查询配置连接数。

### 8.5 容量估算

按 1000MiB/文件、10 人并发、8MiB 分片：

- 一批上传总量约 10GiB；
- API 入站和出站各约 10GiB；
- 千兆全双工下，10GiB 单向满速约 85 秒，实际上传会分布在数分钟内；
- 每 1000MiB 文件约 125 个分片请求，10 人约 1250 个请求；
- 单分片超时 120 秒，需同步调整 API、反向代理和 S3 客户端超时。

## 9. 前端交互

### 9.1 前端状态

| 状态 | 含义 |
| --- | --- |
| `PENDING` | 排队等待 |
| `HASHING` | 正在计算全文件 SHA-256 |
| `UPLOADING` | 分片上传中 |
| `PAUSED` | 用户暂停 |
| `COMPLETING` | 已提交完成，等待合并 |
| `PROCESSING` | 解析或索引处理中 |
| `SUCCESS` | 全部完成 |
| `ERROR` | 失败 |
| `CANCELLED` | 已取消 |

状态流转：

```text
PENDING -> HASHING -> UPLOADING -> COMPLETING -> PROCESSING -> SUCCESS
                         │
                         ├──> PAUSED -> UPLOADING
                         └──> ERROR
```

### 9.2 队列与并发

- 同一时间只上传一个文件；
- 当前文件 2 个分片并发；
- 其他文件在队列中等待；
- 当前文件完成或失败后，自动开始下一个；
- 10 个用户 × 2 个分片 = 20，与服务端全局在途分片上限一致。

### 9.3 进度计算

- 已完成分片字节数 + 在途分片 `upload.onprogress.loaded`；
- 除以文件总大小得到百分比；
- 暂停或重试时将当前分片 `loaded` 归零；
- 恢复上传时用服务端返回的 `uploadedParts` 初始化已完成字节；
- 传输进度使用 XHR 的 `upload.onprogress`。

### 9.4 暂停、恢复与取消

暂停：

- 仅在 `UPLOADING` 状态可用；
- 调用 `AbortController.abort()` 中止在途分片；
- 不调用取消接口，已上传分片保留在 S3；
- 状态置 `PAUSED`，释放并发槽位。

恢复：

- 调用 `GET /api/uploads/{uploadId}` 获取最新 `uploadedParts`；
- 只上传缺失分片；
- 如果会话已过期或已取消，提示重新选择文件。

取消：

- 中止在途请求；
- 调用 `DELETE /api/uploads/{uploadId}`；
- `204` 清理本地记录；
- `409 UPLOAD_ALREADY_COMPLETED` 提示已完成；
- `409 UPLOAD_COMPLETING` 提示正在合并；
- 网络错误保留记录，允许重试取消。

### 9.5 重试

分片：

- 网络错误、`429`、`5xx`：最多 3 次，退避 1s / 2s / 4s；
- `429 UPLOAD_BUSY` 按 `Retry-After` 等待；
- 其他 `4xx` 不重试。

完成：

- 网络错误、`5xx`：退避重试；
- `202`、`409 UPLOAD_COMPLETING`：轮询状态；
- `409 UPLOAD_INCOMPLETE`：补传缺失分片后重试；
- `410`：停止并清理；
- 客户端完成请求超时 180 秒，超时后先查询会话状态。

### 9.6 完成与任务轮询

完成后使用 `taskId` 轮询 `GET /api/tasks/{taskId}`：

- `PENDING`：显示“排队中”；
- `RUNNING`：按 `stage` 展示阶段，更新 `progress`；
- `COMPLETED`：置 `SUCCESS`；
- `FAILED`：置 `ERROR`，展示 `errorMessage`；
- 轮询间隔 2 秒；
- 页面隐藏时暂停轮询，恢复可见后继续；
- 进入终态后停止轮询。

### 9.7 刷新恢复

- 上传中的任务使用 `rag.upload.v2` 恢复；
- 已完成上传、正在解析的任务使用 `rag.processing.v2` 保存 `taskId`、`documentId`、`filename`、`startedAt`；
- 页面加载时查询 `GET /api/tasks/{taskId}`；
- 进入终态后移除记录。

## 10. 校验与运行边界

### 10.1 输入校验

| 对象 | 校验规则 |
| --- | --- |
| 文件名 | 去除路径部分，拒绝空名、`.`、`..`、含 NUL、超过 255 字符 |
| 文件类型 | 从扩展名推导，必须在允许列表中 |
| 文件大小 | 大于 0，不超过 `MAX_DOCUMENT_BYTES` |
| 指纹 | 64 位小写十六进制 |
| 分片号 | 1 到 `totalParts` |
| 分片大小 | 非最后一片等于 `chunkSize`，最后一片等于剩余大小 |
| `Content-Length` | 必须存在，且与实际读取字节数一致 |
| 对象键 | 由服务端生成，校验 UTF-8 字节数不超过 1024 |

### 10.2 数据一致性

- `document_id` 在初始化阶段生成，贯穿上传会话、文档、任务和后续解析产物；
- `upload_id`、`document_id`、`task_id` 均为 32 位十六进制随机值；
- 对象键格式固定为 `documents/{document_id}/source/{filename}`；
- 完成上传的三处写入在同一事务中完成；
- 重复完成、重复取消、重复分片均按幂等处理；
- 分片状态以 `ListParts` 为准，不使用本地文件或 Redis 维护第二套状态。

### 10.3 运行边界

- 服务部署在内网，API 与对象存储通过内网访问；
- 上传链路中浏览器只访问 API，不直接访问 S3 接口；文件下载/预览通过文件访问服务；
- S3 接口不暴露给浏览器；
- CORS 只允许配置的前端来源，并允许 `PUT`；
- 错误响应不返回堆栈、SQL 或对象存储内部细节；
- 日志记录 `upload_id`、`document_id`、`task_id`，不记录文件正文；
- 上传服务不保存完整文件，单个请求只缓冲一个分片。

### 10.4 支持的文件类型

| 扩展名 | 说明 |
| --- | --- |
| `pdf` | PDF 文档 |
| `doc`、`docx` | Word 文档 |
| `xls`、`xlsx` | Excel 表格 |
| `csv` | CSV 文本 |
| `txt` | 纯文本 |
| `md`、`markdown` | Markdown |

### 10.5 数据保留

| 数据 | 保留策略 |
| --- | --- |
| 上传会话 | 活跃期 24 小时；终态保留 30 天 |
| Multipart Upload 分片 | 会话取消或过期后立即清理；孤儿 Multipart Upload 宽限 24 小时 |
| 已完成对象 | 随文档生命周期保留 |
| 孤儿对象 | 终态后保留 7 天再清理 |
| 解析任务 | 按文档版本保留 |
