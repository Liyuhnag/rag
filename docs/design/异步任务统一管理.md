# 异步任务统一管理

日期：2026-10-30。状态：设计草案，尚未实现。需求与验收归属 GitHub [#20](https://github.com/Liyuhnag/rag/issues/20)，关联 #21–#24。

## 目标与边界

解析、合并、切分和索引统一接入 `services/task_runtime/`，由公共层管理执行权、续租、状态迁移、恢复、重试与投递。版本过期是生命周期中的一种确定性失败，#21 作为公共机制的验收场景。

首批接入对象是 `document_tasks` 及其 MinerU 分段协作链路。Celery 负责消息传输和执行，MySQL 保存任务的权威状态；消息允许重复或丢失后补投。

| 层 | 职责 |
| --- | --- |
| 公共运行时 | claim、执行批次标识、renew、进度、阶段交接、complete/fail、recover/retry、按阶段投递 |
| 文档任务策略 | 校验 `parse_version`、进入 PROCESSING、失败状态桥接、各阶段恢复入口与产物保留规则 |
| 阶段处理器 | 解析、提交 MinerU、下载与合并、切分、表结构保存、索引等业务动作，返回明确结果 |
| 持久化适配器 | 条件更新、事务、锁与检查点；确保运行时契约在数据库中成立 |

版本的业务含义由文档策略提供。公共层统一执行校验及失败规则，避免每个 worker 自行比较版本、标记失败。

## 统一执行契约

领取成功返回 `ExecutionContext`，至少包含 task_id、stage、执行批次和 lease_token。业务版本作为文档任务上下文随同传递。领取返回的 token 必须来自本次成功的条件更新，不能更新后再读到别人的 token 并据为己有。

1. 消费者通过公共入口领取指定阶段；未领取成功则结束本次消息消费。
2. 在业务动作前执行文档版本门禁，并按阶段更新文档状态。文档版本与任务版本相等才执行；文档版本更高记为过期，任务版本更高记为版本不一致。版本分配由创建新版本的业务入口负责。
3. 本地执行期间由运行时续租；进度刷新统一经过运行时。续租返回成功或执行权失效，数据库不可用时停止受保护的写入与发布，不能当作续租成功。
4. 处理器返回 `Completed`、`Advance(next_stage)` 或 `AwaitExternal(checkpoint)`。业务异常统一进入失败处理；明确的版本不一致结果转换为任务失败。
5. 丢失执行权时停止后续写入，不再尝试将任务或文档标为失败。过期失败只结束旧任务，保留当前文档版本的状态与产物。

正常处理完成、阶段交接和等待外部结果均有持久化结果。运行时不得把处理器无结果返回自动解释为完成，也不得把它留作无人管理的 RUNNING。

核心操作建议为 `claim`、`renew`、`progress`、`advance`、`await_external`、`resume`、`complete`、`fail`、`retry`、`recover` 和 `dispatch`。worker 通过这些接口推进生命周期，ORM 继续负责 SQL。

## 执行权与数据库一致性

任务状态、进度、阶段和终态更新统一验证执行批次、token、预期阶段及状态；token 为必填。recover、retry 和阶段交接都使旧执行失效。新消费者自行领取，消息只携带定位信息，不能凭消息授予执行权。

需要同时改变任务和文档的操作，在同一数据库事务内校验执行权与版本，再提交两者的更新。仅有 `fail(token)` 成功后再独立调用 `mark_failed(version)`，仍存在两次操作间被 retry 接管的窗口。跨表操作采用一致的加锁顺序。

开始前的一次校验只减少无效计算。产物指针发布、切分数据替换、READY 发布等持久化边界继续复核版本与执行权，防止计算过程中版本或领取者变化。

S3、MinerU、Milvus 和 Elasticsearch 无法加入 MySQL 事务。外部写入保留确定性 ID、版本隔离和重放策略；同版本产物在有覆盖风险时使用执行批次隔离的临时 key，再条件发布指针。版本与 token 校验不能撤回已经发出的外部请求。索引接入时保留现有文档行锁、重放前取消 READY 和双索引核对规则。

## 阶段交接与可靠投递

`advance` 在事务内保存下一阶段及检查点，将任务设为可领取并撤销旧执行权；提交后按阶段投递。投递失败保留可补投状态，维护任务按同一策略补投。目标 worker 自行 claim，重复消息由领取条件拦截。

INDEXING 直接投 `index` 队列；解析、合并与切分按各自可恢复入口投递。持久化策略至少包含：目标队列、执行入口、租约时长、续租间隔、恢复入口与重试准备动作。阶段名本身不足以表达这些行为。

原 `services/parsing/dispatch.py`、`services/indexing/flow.py`、维护任务和 retry API 的投递逻辑统一收拢到运行时。迁移 INDEXING 时，同时调整目前“消费已领取 RUNNING 任务”的约定及对应测试。

## MinerU 外部等待

`AwaitExternal` 表示本地 worker 已交还执行权，远端工作继续进行。保存已提交分段及远端 job 标识，由持久化的轮询计划驱动后续执行。本地 worker 的 lease 与远端处理期限分别管理。

为兼容现有任务查询，首版可保留对外 `RUNNING + PARSING`，在持久化运行元数据中区分本地执行和外部等待。recover 必须读取该区别；健康的远端等待不能因本地没有心跳被重新提交。

分段记录与轮询、下载、重提消息需关联执行批次。旧批次的晚到结果不能借用任务当前 token；读取到新 token 不等于获得其执行权。`resume` 需条件校验批次、版本与等待状态，再授予新的本地执行权。多个分段全部就绪时，只允许一次进入合并。

恢复顺序优先查询已有远端 job、复用已下载结果或重新合并。远端提交成功但本地记录失败的窗口需有明确对账或幂等策略；运行时本身不能保证远端请求恰好执行一次。

## 恢复与重试策略

recover 处理执行失联；retry 处理业务失败后的显式重跑。两者共用阶段策略，分别校验准入条件。

| 阶段或模式 | 恢复与重试行为 |
| --- | --- |
| 本地解析/拆分 | 根据检查点重放；检查旧执行是否仍可能写入固定 key |
| 外部解析等待 | 恢复轮询；按远端状态与现有分段判断是否需要重提 |
| 合并 | 复用完整分段结果，重新生成并条件发布产物 |
| 切分/表结构 | 复用本版本已发布的解析产物，事务替换派生数据 |
| INDEXING | 复用 MySQL 子块，按现有取消 READY、重放、核对及发布流程执行 |
| 版本过期 | 结束旧任务，拒绝该版本重试，保留新版本文档 |

任务 COMPLETED 与文档 READY 含义不同。CSV/XLSX 当前以“结构已保存，待数据入库”为任务完成结果；索引任务必须保留 READY 已发布但任务完成标记尚未提交时的恢复规则，不能因为收尾故障把已发布文档改成失败。

## 落地方式与验收

调整 #20 的实施顺序：先定义并实现公共运行时及文档策略，再逐个接入阶段。#21–#24 分别保留版本、执行权、恢复投递和重试矩阵的验收责任，在同一套运行时中实现。

1. 建立带执行权条件的生命周期持久化操作和公共入口，复用现有 token 机制；明确执行批次、等待模式及检查点的存储结构。
2. 先接入本地解析、切分和表结构路径，覆盖正常首跑、启动前/运行中版本变化、旧执行失效和显式收尾。
3. 接入 MinerU 分段链路，覆盖外部等待、部分提交、晚到回调、多个分段竞争合并和失联恢复。
4. 接入 INDEXING，统一目标 worker claim 和阶段投递，保留现有 READY 与重放保护。
5. 接入维护任务和 retry API，收拢历史入口，完成跨阶段契约测试与故障恢复验证。

验收重点是公共契约对所有阶段成立：重复消息只获得一次执行权；旧执行不能更新新执行；过期任务明确失败；外部等待能持续推进；阶段提交后投递失败仍可补投；业务发布与任务收尾之间的故障可恢复。测试必须断言任务与文档的最终状态。
