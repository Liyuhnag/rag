## 1. 概述

### 1.1 编写目的

本文档定义生成阶段的查询理解与改写，包括改写触发条件、改写类型、LLM 改写 Prompt、输出校验、多查询检索与融合、失败回退和缓存，作为查询理解模块开发、测试和验收的依据。

### 1.2 适用范围

本文档适用于：

- 多轮对话中的指代消解和上下文补全；
- 口语化问题的规范化；
- 多意图问题的拆解；
- 时间、范围、文件类型等过滤条件的抽取；
- 检索关键词扩展（可选）；
- 多查询并行检索和结果融合；
- 改写失败的回退、超时和缓存。

本文档不覆盖：

- 查询向量化（见 RAG-RET-010）；
- 检索执行和父块聚合（见 RAG-RET 文档集）；
- 答案生成和引用校验（见 RAG-GEN-030、RAG-GEN-040）。

### 1.3 术语与缩略语

| 术语 | 说明 |
| --- | --- |
| 查询理解 | 分析用户问题意图，输出改写查询、子查询和过滤条件。 |
| 指代消解 | 把"它、这个、上面说的"替换成对话中具体对象。 |
| 问题拆解 | 把一个多意图问题拆成多个可独立检索的子问题。 |
| 过滤条件抽取 | 从问题中识别时间、范围、文件类型等结构化条件。 |
| 多查询检索 | 使用改写后的主查询和多个子查询分别检索，再融合结果。 |
| 快速路径 | 不需要改写时直接使用原始问题，节省延迟。 |
| 多查询 RRF | 对多个查询的父块排名再做一次 RRF 融合。 |

### 1.5 设计目标

- 多轮对话里的指代和省略能被正确补全；
- 口语问题能转成可检索的书面查询；
- 复杂问题能拆成 1-3 个子问题，分别检索再融合；
- 能从问题中抽出时间、范围、类型等过滤条件；
- 改写失败或超时回退原始问题，不影响答题主流程；
- 每次改写结果可追溯、可评估。

## 2. 非目标

- 不做用户意图分类到固定业务动作（如"查订单""办业务"）；
- 不做实体链接和知识图谱查询；
- 不做同义词词典维护（后续可配置）；
- 不做 query 纠错和拼音纠错；
- 不做多语言翻译；
- 不做用户画像和个性化改写。

```python
class QueryUnderstandOutput:

```

`RetrievalFilters`：

```python
class RetrievalFilters:
    document_ids: list[str] | None

```

## 4. 改写类型

### 4.1 指代消解与上下文补全

| 用户原话 | 历史上下文 | 改写结果 |
| --- | --- | --- |
| "那它呢？" | 上一轮在问"华东区收入结构" | "2026 年华东区收入结构是什么？" |
| "去年呢？" | 上一轮在问"2026 年收入" | "2025 年收入情况是什么？" |
| "上面说的那个方案，成本多少？" | 上文提到"混合检索方案" | "混合检索方案的成本是多少？" |
| "他负责的项目进度怎么样？" | 上文提到"张工" | "张工负责的项目进度怎么样？" |

规则：

- 只使用历史中明确出现过的对象补全，不引入新事实；
- 无法确定指代对象时，保留原始表述，降低 confidence；
- 时间相对词（去年、上个月、Q3）结合当前日期换算成明确年份/区间。

### 4.2 口语规范化

| 用户原话 | 改写结果 |
| --- | --- |
| "帮我看看那个卖得咋样" | "销售数据和销量趋势" |
| "这玩意儿靠谱不" | "该方案的可靠性评估" |
| "收入咋样，跟去年比呢" | "收入情况以及同比变化" |

规则：

- 保留原始意图，只做表达规范化；
- 不变更问题范围，不补充用户没问的内容；
- 口语词表作为 Prompt 示例，不维护硬编码映射。

### 4.3 问题拆解

满足以下任一条件时拆解：

- 一句话包含多个疑问点（"……是多少，为什么……"）；
- 出现"分别、各自、对比、以及、还有"等并列词；
- 问题跨越多个文档或数据范围；
- 主问题包含需要独立检索的子条件。

示例：

```text
原问题：华东和华南的收入差多少，为什么？

rewritten_query：华东和华南的收入差异及原因
sub_queries：
  1. 华东区收入是多少
  2. 华南区收入是多少
  3. 收入差异的原因是什么
```

规则：

- 子查询数量 0-3，超过 3 个只保留最相关的 3 个；
- 子查询必须可独立检索，不依赖指代；
- 主查询保留整体语义，子查询负责覆盖细节；
- 简单问题不拆解，`sub_queries=[]`。

### 4.4 过滤条件抽取

从问题中识别结构化条件，并与请求携带的条件合并：

| 类型 | 示例 | 处理 |
| --- | --- | --- |
| 文件类型 | "在 PDF 里找"、"Excel 表格里" | 映射为 `file_types` |
| 时间范围 | "2026 年"、"上季度" | 记入 `filters.time_range`，当前用于日志和后续扩展 |
| 文档名称 | "《2026 年财务报告》里" | 后续版本支持按文档名解析为 `document_ids` |
| 范围 | "只看华东区" | 不转过滤条件，保留在 query 中 |

规则：

- 请求显式传入的 `document_ids`、`file_types` 优先，抽取结果不覆盖显式条件；
- 抽取结果必须通过白名单校验（文件类型枚举）；
- 无法确定时不抽取，宁可不过滤。

### 4.5 关键词扩展（可选）

- 默认关闭，由 `QUERY_KEYWORDS_ENABLED` 控制；
- 用途：为 ES 关键词检索补充同义词或专业术语；
- 输出 0-10 个关键词，只作为日志和后续 ES 查询扩展的输入；
- 本期不把关键词直接拼进 query，避免引入噪声。

### 4.6 不触发改写的情况

以下情况走快速路径，直接使用原始问题：

- 首轮对话，问题自包含且长度 ≥ 10；
- 问题不含指代词、时间相对词和并列结构；
- 问题本身就是明确的检索式（包含专有名词或编号）。

指代词参考列表：

```text
它、他、她、其、该、此、这个、那个、这些、那些、上面、前面、刚才、上述、呢
```

时间相对词参考列表：

```text
今年、去年、明年、上个月、这个月、下个月、上季度、本季度、最近、当前
```

## 5. 改写实现

### 5.1 流程

```text
输入问题 + 历史
  │
  ├── 规则判断是否需要改写
  │     不需要 -> 直接返回原始问题（method=skipped）
  │
  ├── 查询缓存命中 -> 直接返回（method=cache）
  │
  ├── 调用 LLM 改写（结构化 JSON）
  │     解析失败/超时/低置信度 -> 回退原始问题（method=fallback）
  │
  ├── 校验输出（长度、子查询数量、过滤枚举）
  │
  └── 返回 QueryUnderstandOutput
```

### 5.2 改写 Prompt

```text
你是企业知识库的查询改写助手。请根据对话历史和当前问题，输出一个 JSON 对象。

要求：
1. 指代消解：把"它、这个、那个、上面说的"等替换为历史中明确出现的对象；
2. 口语规范化：把口语表达转成适合检索的书面表达；
3. 问题拆解：只有多意图问题时才拆解，子查询最多 3 个，必须能独立检索；
4. 过滤抽取：识别文件类型（pdf/word/excel/csv/markdown/ppt）和时间范围；
5. 不添加历史中不存在的信息，不改变原始意图；
6. 无法确定时，rewritten_query 使用原始问题，confidence 降低；
7. 只输出 JSON，不输出解释、Markdown 代码块或其他文字。

输出字段：
{
  "rewritten_query": "改写后的主查询",
  "sub_queries": ["子查询1", "子查询2"],
  "filters": {"file_types": ["pdf"], "time_range": {"start": "2026-01-01", "end": "2026-12-31"}},
  "keywords": ["关键词1", "关键词2"],
  "is_follow_up": true,
  "confidence": 0.95
}

对话历史：
{history}

当前问题：
{question}
```

调用参数：

| 参数 | 值 | 说明 |
| --- | --- | --- |
| `model` | `QUERY_REWRITE_MODEL`，默认 `qwen-plus` | 可切换轻量模型 |
| `temperature` | `0.1` | 改写要求稳定 |
| `max_tokens` | `512` | 输出很短 |
| `response_format` | `json_object`（如支持） | 强制 JSON |
| 超时 | `QUERY_REWRITE_TIMEOUT_SECONDS`，默认 8s | 超时回退 |
| 重试 | 1 次 | 仅针对 429/5xx |

### 5.3 输出校验

| 字段 | 校验规则 | 不通过处理 |
| --- | --- | --- |
| `rewritten_query` | string，1-1024 字符 | 回退原始问题 |
| `sub_queries` | 数组，0-3 项，每项 1-512 字符 | 丢弃超限项 |
| `filters.file_types` | 白名单枚举，最多 20 个 | 丢弃非法值 |
| `filters.time_range` | 合法日期区间 | 置空 |
| `keywords` | 数组，0-10 项 | 截断 |
| `is_follow_up` | bool | 默认 false |
| `confidence` | 0-1 | 小于 0.5 视为低置信度，回退原始问题 |

低置信度策略：

- `confidence < 0.5`：使用原始问题检索；
- `0.5 ≤ confidence < 0.8`：使用改写结果，但标记 `degraded=true`，记录日志；
- `confidence ≥ 0.8`：正常使用。

### 5.4 安全要求

- 改写 Prompt 中不包含系统密钥和敏感配置；
- 历史消息进入 Prompt 前截断到 token 预算；
- 只输出 JSON，解析失败直接回退，不执行任何模型输出的"指令"；
- 改写结果不直接返回给用户，除非请求显式要求。

## 6. 多查询检索与融合

### 6.1 检索调用

```text
queries = [rewritten_query] + sub_queries  # 最多 4 个
for q in queries:
    result = RetrievalService.search(
        query=q,
        top_k=top_k,
        document_ids=filters.document_ids,
        file_types=filters.file_types,
    )
```

规则：

- 查询之间并行调用，总超时不超过检索预算；
- 单个查询失败不影响其他查询；
- 全部失败才返回检索不可用；
- 结果包含父块 RRF 分数和 `matched_children`。

### 6.2 多查询融合

每个查询的结果先按分数排序，得到父块排名，再做多查询 RRF：

```text
score_multi(parent) = Σ_q 1 / (RRF_K + rank_q(parent))
```

其中：

- `rank_q(parent)` 是父块在第 q 个查询结果中的排名；
- 未出现该父块的查询不参与求和；
- `RRF_K` 复用检索阶段的 `RRF_K`，默认 60；
- 主查询和子查询默认等权，后续可配置权重。

### 6.3 结果合并

- 以 `parent_id` 去重；
- 保留 `matched_children`，合并后按命中次数排序；
- 排序键：`score_multi` 降序 → `matched_child_count` 降序 → `parent_index` 升序；
- 取 `top_k` 个父块进入上下文组装；
- 记录每个父块来自哪些查询，便于排查。

### 6.4 融合示例

```text
查询 A（主）：父块 P1(1)、P2(2)
查询 B（子）：父块 P2(1)、P3(2)

score_multi(P1) = 1/(60+1) ≈ 0.01639
score_multi(P2) = 1/(60+2) + 1/(60+1) ≈ 0.03252
score_multi(P3) = 1/(60+2) ≈ 0.01613

排序：P2 > P1 > P3
```

## 7. 回退、缓存与超时

### 7.1 回退

| 情况 | 回退行为 |
| --- | --- |
| 模型超时 | 使用原始问题，`degraded=true`，原因 `GEN_REWRITE_FAILED` |
| 模型限流 | 重试 1 次，仍失败回退 |
| JSON 解析失败 | 回退原始问题 |
| 校验不通过 | 回退原始问题 |
| 低置信度 | 回退原始问题 |
| 部分子查询失败 | 使用成功的查询，标记 `SUB_QUERY_PARTIAL` |

### 7.2 缓存

缓存键：

```text
sha256(QUERY_REWRITE_MODEL + ":" + question + ":" + hash(history_tail))
```

规则：

- 默认 TTL 600 秒，进程内 LRU，容量 500；
- 只缓存成功且 `confidence ≥ 0.8` 的结果；
- 多轮问题依赖历史，历史变化时缓存键变化；
- 敏感场景可关闭缓存。

### 7.3 超时预算

| 步骤 | 超时 |
| --- | --- |
| 规则判断 | 立即 |
| 缓存查询 | 10ms |
| LLM 改写 | 8s |
| 输出校验 | 10ms |
| 多查询检索 | 30s（由检索阶段预算控制） |

改写失败不占用后续重试机会，主链路继续。

## 8. 数据记录

改写结果存入 `conversation_messages`：

| 字段 | 内容 |
| --- | --- |
| `rewritten_query` | 改写后的主查询 |
| `sub_queries_json` | 子查询列表 |
| `filters_json` | 抽取和合并的过滤条件 |
| `timing_json.rewrite` | 改写耗时 |
| `degraded` | 是否回退 |
| `error_code` | `GEN_REWRITE_FAILED` 等 |

记录规则：

- 改写成功和失败都记录，便于评估；
- 不记录 Prompt 全文，只记录输入问题和输出结果；
- 日志中不记录完整问题原文。

## 10. 错误处理

| 错误 | code | 可重试 | 处理 |
| --- | --- | --- | --- |
| 改写超时 | `REWRITE_TIMEOUT` | 是 | 回退原始问题 |
| 改写限流 | `REWRITE_RATE_LIMITED` | 是 | 退避重试 1 次 |
| 鉴权失败 | `REWRITE_AUTH_FAILED` | 否 | 回退并告警 |
| 输出解析失败 | `REWRITE_BAD_RESPONSE` | 否 | 回退原始问题 |
| 输出校验失败 | `REWRITE_INVALID_OUTPUT` | 否 | 回退或部分采用 |
| 低置信度 | `REWRITE_LOW_CONFIDENCE` | 否 | 回退原始问题 |
| 子查询部分失败 | `SUB_QUERY_PARTIAL` | 是 | 使用成功结果 |

## 11. 测试

### 11.1 单元测试

- 规则判断是否触发改写；
- 指代消解、时间换算、并列词识别；
- JSON 解析、字段校验、长度截断；
- 低置信度回退；
- 多查询 RRF 计算和去重；
- 过滤条件合并和枚举校验；
- 缓存键计算和命中。

### 11.2 集成测试

- "那它呢？"在上下文中改写出完整问题；
- 多意图问题拆成 3 个子查询并分别检索；
- 子查询结果按 RRF 正确合并；
- 改写超时回退原始问题，答案仍能返回；
- 缓存命中不调用模型；
- 过滤条件与请求条件合并正确。

### 11.3 故障测试

- 模型 429：重试后成功或回退；
- 模型返回非法 JSON：回退；
- 部分子查询检索失败：使用成功结果；
- 全部检索失败：返回检索错误码。

| AC-QU-05 | 多查询结果按 RRF 融合，无重复父块 | 单元测试 |
| AC-QU-06 | 改写失败、超时、低置信度都会回退原始问题 | 故障注入测试 |
| AC-QU-07 | 改写结果落库，可追溯、可评估 | 集成测试 |
| AC-QU-08 | 快速路径不调用模型，延迟明显降低 | 性能测试 |

## 13. 风险与应对措施

| 风险编号 | 风险描述 | 影响 | 应对措施 |
| --- | --- | --- | --- |
| R-QU-01 | 改写改变用户意图 | 答非所问 | 低置信度回退、Prompt 约束、保留原始问题 |
| R-QU-02 | 指代消解错误 | 检索错对象 | 只使用历史明确对象，无法确定则保留原表述 |
| R-QU-03 | 子查询过多 | 延迟和成本上升 | 限制 3 个，按优先级截断 |
| R-QU-04 | 多查询融合引入噪声 | 相关性下降 | RRF 融合、主查询保留、离线评估 |
| R-QU-05 | 改写模型不可用 | 延迟增加或回退 | 超时回退、快速路径、缓存 |
| R-QU-06 | 历史过长导致 Prompt 超限 | 改写失败 | 历史截断和摘要，只保留相关轮次 |
| R-QU-07 | 改写结果包含敏感信息 | 合规风险 | 不记录全文、日志脱敏、缓存可关闭 |
