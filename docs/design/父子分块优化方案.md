# RAG 父子分块（Parent-Child Chunking）优化方案

日期：2026-11-01
状态：设计草案（待评估）
涉及模块：
- `backend/services/chunking/`（`source.py`、`splitter.py`、`service.py`、`common/models.py`）：切分流水线主体；
- `backend/model/document_chunk/`（`model.py`、`orm.py`）+ 迁移 `db/migrations/0005_chunk_context_prefix.sql`：新增 `context_prefix`、`heading_keys` 两列；
- `backend/services/indexing/`（`service.py`、`elasticsearch.py`）：向量化文本拼接与 ES 字段；
- 检索服务：跨章节引用解析（第五章）。

## 一、背景与现状问题

### 1.1 为什么采用父子分块？
在 RAG 系统中，**检索召回**与**大模型生成**对文本块粒度存在天然矛盾：
- **检索侧（Milvus 向量检索 + Elasticsearch BM25）要求粒度细**：文本块过大时，多主题语义混杂会稀释核心特征。参与检索的**子块（`CHILD`）**控制在 `400 tokens`，带 `80 tokens` 重叠。
- **生成侧（LLM 上下文）要求语义完整**：仅把 400 tokens 碎片交给大模型，容易缺失前置条件、完整条款或完整表格。因此保留章节级**父块（`PARENT`）**，**父块只存 MySQL、不向量化**；检索命中子块后，通过 `parent_id` 回表取父块交给大模型。

### 1.2 上游解析产物的实际形态
CHUNKING 阶段只处理非结构化文档，输入形态如下；表格类文件不进入本阶段：

| 文件类型 | 产物路径 | 输入形态 | 本方案处理路径 |
| :--- | :--- | :--- | :--- |
| PDF / DOC / DOCX | MinerU 合并 JSON 无 `blocks` → 读 `merged.md` | 逐行 `verbatim` 文本 + `<!-- page: N -->` 页标记 | **Markdown 流水线**（第四章全部步骤） |
| Markdown (`.md`) | 本地 `blocks` | 至多 64Ki 字符的 `verbatim` 碎片（需原样拼接后再按行处理），**无页码概念** | **Markdown 流水线**（跳过页码映射、孤立页码行、页眉页脚统计；`page_start/page_end` 为 NULL） |
| 纯文本 (`.txt`) | 本地 `blocks` | 首块为 `# 文件名`（`heading_path=文件名`），其后按空行分段 | **Markdown 流水线**（隐式标题识别对其同样有效） |
| CSV / XLSX | — | `kind="table"` 的 JSON 行记录 | **不进入 CHUNKING**，走结构化入库（`services/structured/`）+ NL2SQL 查询 |

### 1.3 现有切分方案的痛点

| 编号 | 痛点 | 具体表现与后果 |
| :--- | :--- | :--- |
| **1** | **父块未按标题切分，且被页码/行数硬截断** | `source.py` 不解析 `#` 标题（`heading_path` 全为空）；`_groups` 在翻页、满 128 行、`locator` 拼接超过 512 字符时强制断开，再用 `SentenceSplitter(1600)` 截断，同一章节被拆成多个碎片父块。 |
| **2** | **标题噪音、层级扁平与隐式标题漏识别** | OCR 产物中存在 `#xx`、`# 第 3 页` 等**伪标题**；MinerU 常把所有标题都输出为同级 `#`，**层级信息丢失**；中文制度、合同常用 `**第一章**`、`**（一）**`、`1.1` 等无 `#` 的编号标题，整篇切不出章节。 |
| **3** | **跨章节引用断裂** | 「详见第三章」「按 4.2 节执行」的引用句与被引用章节失联，LLM 看不到被引用条款。 |
| **4** | **简称指代丢失** | 开头定义「北京XX科技有限公司（以下简称“甲方”）」，后续子块只剩「甲方」，无法通过主体全称命中。 |
| **5** | **Markdown 特殊语法块被拦腰切碎** | 表格、代码块、公式块被 `SentenceSplitter` 从中间切断，下半段表格丢失表头，代码围栏不闭合。 |
| **6** | **目录页、页眉页脚与超短碎片污染** | 目录页包含全书关键词，抢占 Top-K 却无正文信息；光杆标题、极短父块和尾部碎片产生低质向量。 |
| **7** | **中文分句失效** | `PunktSentenceTokenizer` 只认英文句点，中文长段落只能按 token 硬切，句子被拦腰截断。 |
| **8** | **子块页码不准** | 子块直接继承父块页码，跨页父块下的子块无法定位到实际所在页。 |

## 二、设计原则

1. **`content` 保持原文**：父子块 `content` 只做**删除噪音行**这一种改动，不插入括注、不埋链接锚点。父块是给 LLM 与用户看的证据，必须能和原文逐字对照、可高亮、可回溯页码。
2. **增强只进向量化文本**：简称释义、标题路径等上下文只拼接到送入 embedding / ES 的文本中（沿用 `indexing/service.py:71` 已有的 `heading_path + content` 拼接方式），不污染原文。
3. **跨章引用在检索时解析**：切分时为父块记录标题编号键 `heading_keys`，检索阶段按编号匹配，切分阶段不依赖 `parent_index`，从而消除步骤间的循环依赖。
4. **允许接入自研微调模型**：首版以正则 + 行级结构扫描实现；CHUNKING 阶段可接入自研微调模型（如标题识别、图片描述）。模型调用须有超时与降级（失败回退到规则结果或跳过增强），阶段超时按模型耗时调整。
5. **有界资源**：父块有硬上限，整篇内存有上限，超限降级而非失败。
6. **可度量**：先建评测基线，每一步上线前后对比召回指标，没有收益的步骤直接删除。

## 三、总体设计：切分流水线

```
S3 解析产物（CSV/XLSX 不进入本阶段，走 NL2SQL）
  │
  ▼ Markdown 行流 (PDF/DOC/DOCX/MD/TXT)
[步骤 1] 行流装载与页码映射
  │  • 去掉 <!-- page: N --> 标记，记录「行号 → 页码」映射
  │  • 识别代码块 / 公式块 / 表格块边界，块内不参与后续规则
  │  • 提取全文简称字典（供步骤 5 填 context_prefix）
  ▼
[步骤 2] 降噪（只删行，不改写）
  │  • 目录章节 / 目录行；页标记相邻的孤立页码行；跨页重复页眉页脚
  │  • 降噪完成后执行跨页续表拼接
  ▼
[步骤 3] 标题识别与层级重建（只产出结构，不改原文）
  │  • 伪 # 标题降级；隐式编号标题识别（带上下文约束）
  │  • 按编号样式「首次出现顺序」动态分配层级，覆盖 MinerU 的扁平 #
  ▼
[步骤 4] 父块提取（按标题切分 + 硬上限 + 小块合并）
  │  • 标题栈生成 heading_path；跨页聚合 page_start ~ page_end
  │  • 空壳标题向下合并；极小父块与相邻同级合并；超上限按下级结构/段落拆分
  ▼
[步骤 5] 子块切分（语法块感知 + 中英分句 + 碎片合并）
  │  • 表格/代码/公式原子保护或按行拆分并补表头/围栏
  │  • 子块页码由「行号 → 页码」映射计算
  │  • 按步骤 1 的简称字典为每个子块生成 context_prefix（详见步骤 6）
  ▼
写入 document_chunks（content 为原文；context_prefix、heading_keys 为附加列）
```

## 四、各步骤详细设计

### 步骤 1：行流装载与页码映射

1. **整篇装载**：步骤 2（页眉页脚统计）和简称字典提取（详见步骤 6，在本步骤装载完成后执行）需要全篇视图，因此 Markdown 流水线将整篇行流读入内存。
   - 上限：`max_document_chars = 20_000_000`（约 20M 字符，约 80MB 内存）。超限时**降级**：跳过跨页页眉页脚统计与简称字典，其余步骤按流式窗口执行，并记录告警日志。
2. **页码映射**：遇到 `<!-- page: N -->` 时不输出该行，只更新当前页码；为每个保留行记录 `page`。后续删行不影响映射（映射挂在行对象上，而非字符偏移）。
3. **语法块边界识别**：
   - 代码块：```` ``` ```` / `~~~` 围栏，记录语言标识；
   - 公式块：`$$ ... $$`；
   - 表格块：连续的 `|...|` 行（第二行为 `| --- |` 分隔行），或 `<table>...</table>`；
   - 图片块：`![...](...)` 行、紧随其后的图片描述行（`> 图片描述：...`，见下）及图注行（以 `图/Figure` 开头），作为一个整体原子保护。
   - 语法块内的行**不参与**步骤 2、3 的任何规则，避免误删或误判标题。

> **图片描述（后续规划，暂不实施）**：图片链接本身对向量与 ES 检索没有语义。后续在 CHUNKING 步骤 1 内用图文多模态模型为图片生成描述，不新增阶段：
> - **为何不放 MERGING**：MERGING 软超时仅 300 秒，且重试会整份重新合并，不适合逐图调用模型。
> - **调用时机**：步骤 1 识别出图片块后，读取 `assets/part-*/` 下对应图片调用模型。小图（图标、装饰线）跳过，按图片内容哈希去重（如每页 logo 只描述一次）；多张图片并发调用，并发数可配置。
> - **上下文**：调用模型时附带图片前后各一段正文（此时标题尚未识别，标题路径不可用），使描述贴合文档语境。
> - **写入位置**：描述以 `> 图片描述：...` 补在图片行之后，与图片、图注组成一个原子图片块，随子块向量化、随父块交给 LLM。`merged.md` 不改写。
> - **缓存**：CHUNKING 重试会整份重切，因此描述按「图片哈希 + 模型版本」缓存到对象存储（如 `{document_id}/{version}/image_descriptions.json`），重试与重新切分只补缺失项。
> - **超时与降级**：单图调用设超时；单图失败只缺该条描述，不导致 CHUNKING 失败，失败数计入日志。CHUNKING 软超时需按图片数量与并发数上调（现为 900 秒）。
> - **未实施或模型不可用时**：按现状只保留图片链接，其余流程不变。

### 步骤 2：降噪（只删行，不改写）

1. **目录剔除**：
   - **单行目录特征**：`r"^.{1,60}?(?:\.{3,}|…{2,}|·{3,}|-{3,}|\s{4,})\s*\d+\s*$"`；
   - **目录区段判定**（满足任一即整段丢弃）：
     - 标题去符号后为 `目录 / 目 录 / Contents / TABLE OF CONTENTS`，且其下 `≥ 50%` 非空行命中单行目录特征；
     - **无标题兜底**：文档前 10% 页内出现连续 `≥ 5` 行命中单行目录特征；
     - **表格形态目录**：MinerU 常把目录识别为表格，若表格块 `≥ 60%` 行的末列为纯数字页码、且首列匹配章节编号样式，视为目录。
2. **孤立页码行**：匹配 `r"^\s*(?:-\s*\d+\s*-|第\s*\d+\s*页(?:\s*[/／]\s*共\s*\d+\s*页)?|Page\s+\d+(?:\s+of\s+\d+)?|\d{1,4})\s*$"`，**且仅当该行位于页标记前后各 2 个非空行以内**才删除，避免误删正文中单独成行的数字。无页标记的文档（MD/TXT）不执行此规则。
3. **跨页重复页眉页脚**：文档总页数 `≥ 3` 时，取每页首/末各 2 个非空行，去除数字后归一化（长度 `≤ 30` 字）。同一归一化文本在 `≥ max(3, 总页数 × 30%)` 个页面出现，判定为页眉页脚并删除。
4. **跨页续表拼接**（在第 2、3 项删除页码行、页眉页脚之后执行，否则两段表格之间夹着页脚/页眉会导致拼接失败）：MinerU 逐页解析，跨页表格会被拆成两张独立表格，后半张没有表头。对每个页边界，检查边界前后最近的非空行：
   - 前后都是表格（Markdown `|...|` 行或 `<table>`），且列数相同，则把后半张的行直接接到前半张末尾，合成一张表，并更新步骤 1 的表格块边界；
   - 后半张开头如果与前半张表头相同（MinerU 在续表上重复识别了表头），丢弃这几行重复表头；
   - 合并后表格的行仍保留各自原来的 `page`，子块页码照常计算。

### 步骤 3：标题识别与层级重建（只产出结构，不改原文）

本步骤为每一行标注 `heading_level`（`None` 表示正文），**不修改行的字面内容**。父块 `content` 中保留原始的 `**第一章 总则**`。

#### 3.1 伪 `#` 标题降级
以 `#` 开头的行命中以下任一条件，标注为正文：
1. 井号后无空格：`#xx`、`#123`、`#include`（标准标题要求 `^#{1,6}\s+\S`）；
2. 去 `#` 后有效字符数 `> 50`；
3. 以 `。！？；!?;：:` 结尾；
4. 图表题注：`r"^(?:图|表|附图|附表|Figure|Table)\s*[\d一二三四五六七八九十]"`；
5. 纯数字或纯页码样式（`# 3`、`# 第 3 页`）。

#### 3.2 候选标题识别
对非 `#` 行先剥除首尾对称的粗体/斜体符号（`**`、`***`、`__`），满足以下**全部**条件才视为候选标题：
- 单行长度 `≤ 40` 字，不以 `。！？；，,：:` 结尾；
- **上下文约束**：前一行为空行 / 语法块结束 / 文档开头（即独立成段）；
- 行首匹配下表任一**编号样式**：

| 样式 ID | 识别模式 | 示例 |
| :--- | :--- | :--- |
| `chapter` | `^第[一二三四五六七八九十百千0-9]+[章篇部分](?:\s|$)` | `第一章 总则` |
| `section` | `^第[一二三四五六七八九十百0-9]+节(?:\s|$)` | `第一节 定义` |
| `article` | `^第[一二三四五六七八九十百0-9]+条(?:\s|$)` | `第三条 违约责任` |
| `cn_num` | `^[一二三四五六七八九十]+[、.．]\s*\S` | `一、项目背景` |
| `cn_paren` | `^[（(][一二三四五六七八九十]+[)）]\s*\S` | `（一）基本原则` |
| `dec2` | `^\d+\.\d+(?!\.\d)\s+\S` | `1.1 系统架构` |
| `dec3` | `^\d+\.\d+\.\d+\s+\S` | `1.1.1 模块划分` |
| `num_paren` | `^[（(]\d+[)）]\s*\S`（且长度 `≤ 20` 字） | `（1）硬件环境` |

**防误判规则**（命中任一即放弃）：
- `dec2` / `dec3` 后紧跟数量单位或金额词（`万|元|%|倍|个|年|月|日|米|kg`），如「3.5 万元由甲方承担」；
- 同一样式的编号在文档中**不连续**（如只出现孤立的一个 `4.2`，前后无同级 `4.1`/`4.3`/`3.x`），且该行不带粗体包裹也不是已有 `#`。

`#` 开头且未被 3.1 降级的行，同样提取其编号样式（`# 1.1 系统架构` → `dec2`），无编号则样式为 `md_hN`（按 `#` 个数）。

#### 3.3 动态层级分配
固定映射表无法处理「第一章下用一、」或「MinerU 全部输出 `#`」的情况，因此按**样式首次出现的嵌套顺序**分配层级：

1. 样式间存在**先验包含关系**（用于打破歧义）：`chapter > section > article`，`dec2 > dec3`，`cn_num > cn_paren`，`cn_paren > num_paren`。
2. 顺序扫描候选标题，维护一个「样式栈」：
   - 遇到一个**未分配**的样式 S：若栈顶样式 T 与 S 有先验包含关系且 T 包含 S，或 S 在 T 之后首次出现且 S 不包含 T，则 `level(S) = level(T) + 1`；否则 S 与栈中最近一个同类（无包含关系）样式同级。
   - 遇到**已分配**样式：弹出栈中层级 `≥ level(S)` 的样式后压入。
3. 原生 `#` 无编号标题（`md_hN`）：若文档内所有 `#` 标题都是同一个 `#` 级别（MinerU 扁平化特征），按其编号样式参与动态分配；否则保留原生 `#` 个数作为层级。
4. `.txt` 的首行 `# 文件名` 固定为 0 级根标题，不参与 `heading_path` 拼接之外的切分（不单独产出父块）。

**验收样例**（直接作为单元测试，规则描述与样例冲突时以样例为准）：

| # | 输入标题序列（按出现顺序） | 期望层级 |
| :---: | :--- | :--- |
| 1 | `第一章` → `一、` → `（一）` → `第二章` → `一、` | 1 → 2 → 3 → 1 → 2 |
| 2 | `一、` → `1.1` → `1.1.1` → `二、` → `2.1` | 1 → 2 → 3 → 1 → 2 |
| 3 | `第一章` → `第一节` → `第一条` → `第二条` → `第二节` | 1 → 2 → 3 → 3 → 2 |
| 4 | MinerU 扁平：`# 第一章 总则` → `# 1.1 适用范围` → `# 1.1.1 范围说明` → `# 第二章` | 1 → 2 → 3 → 1 |
| 5 | 原生多级 `#`：`# 概述` → `## 背景` → `### 目标` → `## 范围` | 1 → 2 → 3 → 2 |
| 6 | `第一章` → `（一）` → `1.1`（`1.1` 前后无同级编号、无粗体） | 1 → 2 → 正文 |

### 步骤 4：父块提取

#### 4.1 按标题切分
- 每个标题行开启一个新父块，直到下一个标题（任意层级）为止。层级只用于维护标题栈和生成 `heading_path`，不影响父块边界。
- 维护 1~6 级标题栈，`heading_path = " / ".join(栈中标题文本)`，标题文本为剥除 `#`、粗体符号后的纯文本。

#### 4.2 空壳标题向下合并
标题下方无正文、紧接子标题时，不产出空壳父块：只压栈，并把该标题原行拼入下一个父块开头。
例：`**第一章 总则**` 下直接是 `1.1 适用范围`，则父块 `heading_path = "第一章 总则 / 1.1 适用范围"`，`content` 以 `**第一章 总则**\n1.1 适用范围\n...` 开头。

#### 4.3 父块大小约束（新增 `parent_min_tokens` / `parent_max_tokens`）

| 参数 | 默认值 | 说明 |
| :--- | :--- | :--- |
| `parent_max_tokens` | `2500` | 父块硬上限，避免一章上万 token 撑爆 LLM 上下文 |
| `parent_min_tokens` | `120` | 低于此值的父块尝试合并 |
| `child_chunk_size` | `400` | 子块目标大小 |
| `chunk_overlap` | `80` | 子块重叠 |
| `child_min_tokens` | `30` | 尾部碎片合并阈值 |

`ChunkOptions` 用 `parent_max_tokens` / `parent_min_tokens` 取代原 `parent_chunk_size`，校验改为：`0 <= chunk_overlap < child_chunk_size < parent_max_tokens`，且 `child_min_tokens < child_chunk_size`、`parent_min_tokens < parent_max_tokens`。

- **超过上限**：在父块内部按优先级寻找切点——①更下一级但未达到识别阈值的编号行（如 `（1）`）；②语法块边界；③空行段落边界；④句末标点。拆出的各片**共享同一 `heading_path`**，`locator` 追加 `part:2/3`。语法块不在内部切开（超长语法块单独成片，由步骤 5 处理）。
- **低于下限**：与**同一父标题下**的相邻兄弟父块合并（优先向后合并，最后一个向前合并），合并后 `heading_path` 取二者公共前缀 + 首个标题；合并后不得超过 `parent_max_tokens`。不跨一级标题合并。
- **编号键 `heading_keys`**：每个父块记录其覆盖的全部标题编号键（归一化规则见第五章），包括 `heading_path` 各段的编号、被合并父块的标题编号、空壳合并进来的标题编号。例：`4.1`、`4.2` 合并后 `heading_path = "第四章 / 4.1 ..."`，`heading_keys = ["chapter:4", "dec:4.1", "dec:4.2"]`。存入 `document_chunks.heading_keys`（父块填写，子块为 NULL），供第五章跨章引用匹配。
- **全文无标题**：按上述切点规则以 `parent_max_tokens` 为窗口分片，`heading_path` 为文档标题。

#### 4.4 页码与定位
- `page_start` / `page_end`：父块所有行页码的最小/最大值。翻页**绝不**切断父块。
- `locator`：改为区间表达 `page:3-17`（单页为 `page:3`），拆片追加 `;part:2/3`。彻底消除现有「逐页拼接到 512 字符强制断块」的问题。

### 步骤 5：子块切分

#### 5.1 中英混合分句
替换 `PunktSentenceTokenizer`，使用离线正则分句器：
- 断句符：中文 `。！？；…`（含连续 `……`）、换行 `\n`、英文 `[.!?](?=\s)`；
- 保留断句符在前一句末尾；引号、括号闭合符（`”」』）)`）跟随前一句；
- 不在小数点（`3.5`）、编号（`1.1`）、缩写（`e.g.`）处断开。

#### 5.2 语法块保护
父块内容序列化为「普通文本段」与「语法块」序列：

1. **语法块 `≤ child_chunk_size`**：原子保护。当前子块剩余容量够则整块拼入；不够则先产出当前子块，再将语法块放入新子块。
2. **语法块 `> child_chunk_size`**：
   - **表格**：按行切分，第 2 个及之后的子块开头复制表头行 + 分隔行；
   - **代码**：按行切分，前块末尾补 ```` ``` ````，后块开头补 ```` ```lang ````；
   - **公式**：单个公式不拆，超长时整块单独成子块；
   - **补齐后长度检查**：补表头/围栏后的子块不得超过 `embedding_max_input_tokens`（取自 embedding 配置，默认 `8192`）；表头本身超过 `child_chunk_size / 2` 时不再复制表头，改为在子块开头补一行 `列：A, B, C` 的简写。
3. **冒号导语 + 列表**：上方紧邻以 `：`/`:` 结尾的导语行，列表跨多个子块时，后续子块开头冠以该导语行。
4. **重叠规则**：`chunk_overlap` 只在普通文本段之间生效；子块边界落在语法块前后时**不做重叠**（语法块不被复制进上一子块尾部），补表头/导语视为语法续接，不计入重叠。

#### 5.3 碎片合并
父块切完后，若尾部子块 `token_count < child_min_tokens` 且父块不止 1 个子块，合并入倒数第 2 个子块（允许其略超 `child_chunk_size`，但不超过 `embedding_max_input_tokens`），更新 `child_count`。

#### 5.4 子块页码
子块 `page_start` / `page_end` 由其覆盖行的页码映射计算，不再继承父块。`locator` 为子块自身的页码区间。

### 步骤 6：文档级上下文提取（只用于向量化）

> 本步骤不是流水线中的独立顺序步骤：简称字典在步骤 1 整篇装载后提取，`context_prefix` 在步骤 5 生成每个子块时填入。单列一节只为集中说明规则。

#### 6.1 简称字典
扫描全文（跳过语法块），匹配括号简称定义：
`r"([一-龥A-Za-z0-9（）()《》]{4,40}?)\s*[（(](?:以下)?(?:简称|下称|称)[“\"「『]?([^”\"」』）)]{2,12})[”\"」』]?(?:[或、][“\"「『]?([^”\"」』）)]{2,12})[”\"」』]?)?[)）]"`

- 示例：`北京智源科技有限公司（以下简称“甲方”或“本公司”）` → `{"甲方": "北京智源科技有限公司", "本公司": "北京智源科技有限公司"}`。
- 同一简称出现多个全称定义时，以**定义位置之后最近的**为准（按父块顺序生效），避免附件中重定义导致错配。
- 字典上限 200 条。

#### 6.2 写入位置
对每个子块，收集其 `content` 中出现、且全称未在本子块出现的简称，生成：
`context_prefix = "甲方=北京智源科技有限公司；乙方=上海云数信息技术有限公司"`

向量化与 ES 写入文本改为：`heading_path + "\n" + context_prefix + "\n" + content`（空项跳过）。`content` 本身不变，LLM 看到的仍是原文。

> **存储决策**：
> - **MySQL**：`document_chunks` 新增两列可空字段（迁移 `0005_chunk_context_prefix.sql`）：`context_prefix TEXT NULL`（子块填写）、`heading_keys JSON NULL`（父块填写，见 4.3）。旧数据为 NULL，兼容现有读取。`DocumentChunk` 模型与 `orm.py` 的读写语句同步增加这两个字段。
> - **Milvus**：不新增字段，`context_prefix` 只体现在 embedding 输入文本里。
> - **ES**：新增 `context_prefix` 文本字段（与 `content` 同分词器），检索时与 `content`、`heading_path` 一起做多字段匹配，使「北京智源科技有限公司」能命中只写了「甲方」的子块；`elasticsearch.py` 的 mapping 校验同步更新，已有索引需重建或 `put_mapping` 追加字段。

#### 6.3 不做的事及原因
- ~~原地括注「甲方（全称）」~~：修改原文、重复括注、污染证据。
- ~~「该公司 / 该系统」最近实体回填~~：启发式猜错率高，猜错后把错误主体写进证据比漏召回更糟。待评测证明「该 XX」类查询漏召回显著时再评估。
- ~~「本条款 / 上述标准」绑定锚点~~：收益不明确，且依赖 `parent_index`。
- ~~正文中埋 `(#parent:N)` 内联链接~~：改为第五章检索时解析。

## 五、检索时跨章节引用解析

不在切分阶段处理，改由检索服务在回表取父块后执行：

1. 对命中父块的 `content` 匹配引用：
   `r"(详见|参见|见|按照|依据|参照|根据)\s*(第[一二三四五六七八九十百0-9]+[章节条部分](?:第[一二三四五六七八九十0-9]+[节条])?|\d+\.\d+(?:\.\d+)?\s*节?)"`
2. 将引用目标归一化为编号键（中文数字转阿拉伯数字：`第三章` → `chapter:3`，`4.2节` → `dec:4.2`）。
3. 查询同 `(document_id, version)` 下 `chunk_level = PARENT` 的父块及其 `heading_keys`（单文档父块数通常 < 1000，可在请求内一次查出并缓存），按以下规则匹配：
   - **精确命中**：目标键出现在某父块的 `heading_keys` 中即命中，不要求是 `heading_path` 末段。这样合并过的父块（`4.1 + 4.2`）也能被「4.2 节」引用到；
   - **章级目标**（`chapter:N`、`cn_num:N` 等一级样式）：取 `heading_keys` 含该键的父块中按 `parent_index` 排序的前 2 个，即该章的开头部分，避免一次拉入整章；
   - **拆分父块**（`locator` 带 `part:`）：同一标题拆出的多片都含相同键，只取 `part:1`；
   - 命中父块与当前父块相同时跳过。
4. 被引用父块作为**补充证据**追加到上下文，并受 token 预算约束：
   - 每个命中父块最多追加 2 个被引用父块；
   - 补充证据总量不超过上下文预算的 30%，超出时按被引用次数排序截断；
   - 不递归展开（被引用父块中的引用不再追查）。

此设计无需在切分阶段知道 `parent_index`，也不随父块合并/拆分规则变化而失效。

## 六、工程配套

### 评测基线（实施前完成）
- 负责人：待定（需在开发启动前指定），评测文档与标注问题集入库到 `backend/tests/fixtures/chunking_eval/`，评测脚本可一键复跑；
- 选取 5~8 份真实文档：制度类、合同类、技术方案类 PDF 各 2 份，含扫描件 1 份、含大表格 1 份；
- 每份标注 5~8 个问题与其应命中的原文段落，共 30~50 题；
- 记录现方案的子块 Recall@5 / Recall@10、父块命中率、平均父块 token 数，作为基线；
- 每个步骤落地后重跑，**无正向收益的步骤回退**。

### 版本与重建
- 切分算法变更后，同一 `version` 重切结果会不同（chunk ID 由 `parent_index` 派生）。约定：算法变更不复用旧 version，**存量文档通过「重新解析/重新切分」生成新 version**，走现有 `replace_current_version` + 索引 `delete_version` / `prune_older` 流程清理 Milvus 与 ES 旧数据。
- 提供批量重切脚本，按文档分批投递 CHUNKING 任务，限速避免挤占 embedding 配额。

### 可观测性
每次切分记录：父块数、子块数、父块 token 的 P50/P95/最大值、被删噪音行数、识别标题数（按样式）、被拆分的超长父块数、降级标记。用于发现标题识别失效（标题数为 0）或降噪过度（删行比例 > 20%）的文档。

### chunk ID 稳定性
- chunk ID 由 `(document_id, version, parent_index, child_order)` 派生，切分规则（标题识别、合并/拆分阈值、模型版本）任何调整都会使同一文档的 ID 整体变化，因此规则变更一律通过新 version 生效（见「版本与重建」）。
- 现状核对：chunk ID 只出现在 `document_chunks`、Milvus、ES，以及 INDEXING 任务的续跑检查点 `last_chunk_id`（`model/document_task/orm.py`，作用域为单个 version，不受影响）；对话服务目前不保存 chunk ID。
- 约束：后续若在对话记录、引用溯源、用户反馈中需要保存检索证据，**必须同时保存 `version` 和证据原文（或 `page_start/page_end` + `heading_path`）**，不能只保存 chunk ID，否则文档重切后引用将失效。
