# 异步任务重复消费方案

## 1. 技术背景

文档上传采用异步处理。`POST /api/documents` 只负责接收文件并返回任务号，对象存储和 `documents` 记录由后台任务写入。当前任务完成到 `STORED` 为止，表示文件和文档行已经落库；文本分块和向量化尚未接入。

异步框架是 Celery 5.6，消息队列是 Redis 7。任务名为 `rag.process_document`。Redis 库 0 存放待执行消息，库 1 存放 Celery 结果。业务状态以 MySQL 表 `processing_tasks` 为准。监控使用 Flower，不作为处理结果的依据。

Worker 的投递语义是至少一次：


| 配置                           | 取值             | 作用                             |
| ---------------------------- | -------------- | ------------------------------ |
| `task_acks_late`             | 开启             | 任务函数返回后才确认消息                   |
| `task_reject_on_worker_lost` | 开启             | worker 进程异常退出时，未确认的消息退回队列      |
| `worker_prefetch_multiplier` | 1              | 每个进程预先只持有一条消息                  |
| `worker_concurrency`         | 4              | 同时处理 4 条                       |
| `soft_time_limit`            | 60 秒           | 任务内抛出超时异常，记为 `FAILED`，原因「处理超时」 |
| `time_limit`                 | 90 秒           | 杀掉执行进程。该路径会确认消息，不会因此再投递        |
| Redis `visibility_timeout`   | 3600 秒（传输层默认值） | 超过该时间仍未确认的消息重新可见               |


一次处理的现有顺序是：

1. 按任务号读取 `processing_tasks`。行不存在则直接返回并确认。
2. 临时文件不存在则写成 `FAILED`（「临时文件不存在」）并确认。
3. 状态改为 `STORING`，调用 `document_store.add`。该方法每次生成新的文档号，对象键为 `documents/{文档号}/{文件名}`，再插入 `documents`。
4. `finish` 把任务改为 `STORED` 并写入文档号。
5. 删除临时文件。失败时先写 `FAILED`，再删除临时文件。

`documents.id` 是主键。`document_store.add` 不接受外部传入的文档号，两次调用得到两行文档、两个对象。任务状态也没有在入口和更新语句处区分「已经结束」和「仍在处理」。

客户端重复提交 `POST /api/documents` 会生成新的任务号和新的消息。那是两次上传，不在本文范围内。本文只处理同一个任务号被再次执行。

## 2. 重复消费出现的位置

重复消费发生在消息已经被 worker 取走、Celery 尚未确认的区间。这段时间里消息放在 Redis 的未确认集合中。进程在确认前消失，或未确认时间超过 `visibility_timeout`，同一条消息回到 `celery` 列表，`process_document` 会用同一个任务号再执行。

确认发生在任务函数返回之后。函数内部任何一次进程退出，都落在这个区间里。

### 2.1 消息被再次投递的时机


| 时机                                         | 队列上发生的事                                                                     |
| ------------------------------------------ | --------------------------------------------------------------------------- |
| 执行中的 worker 进程被强行终止，包括内存不足、`kill -9`、宿主机重启 | `reject_on_worker_lost` 把未确认消息退回队列                                          |
| 部署或重启时，任务函数还没有返回                           | 未确认消息在 worker 退出时被恢复，随后再次投递                                                 |
| 消息取出后超过 3600 秒仍未确认                         | Redis 按 `visibility_timeout` 使该消息重新可见。硬超时会在 90 秒确认；只有进程失去响应且超时没有生效时，才会走到这一步 |


软超时、业务异常和硬超时都会确认消息。这三条路径结束后，同一条消息不会因为超时或业务失败再进入任务函数。

### 2.2 任务函数中的断点

下面按 `process_document` 的现有步骤列出。进程若在该步骤完成之后、函数返回之前退出，再执行一次的结果如下。


| 断点                               | 当时的状态                                      | 再次执行的结果                                                                  |
| -------------------------------- | ------------------------------------------ | ------------------------------------------------------------------------ |
| 已读到任务行，尚未改为 `STORING`            | `PENDING`，临时文件还在，没有文档行                     | 再跑一遍完整写入。这一次还没有产生第二份文档                                                   |
| `STORING` 已写下，对象或文档行还没写完         | `STORING`，临时文件还在                           | 再次调用 `add`。对象已上传但插入未成功时，现有失败路径会删掉该对象，再执行可以重新上传                           |
| `add` 已返回，`finish` 还没执行          | 对象和 `documents` 行已存在，任务仍是 `STORING`，临时文件还在 | 再次 `add` 生成新的文档号，留下第二份文档。后一次 `finish` 把 `document_id` 指到新行               |
| `finish` 已执行，临时文件还没删             | `STORED`，临时文件还在                            | 入口不看 `STORED`，文件仍在，再次 `add`。任务改指向新文档，前一份文档留在库中                           |
| 临时文件已删，函数还没返回                    | `STORED`，临时文件不在                            | 入口先判断文件，`fail` 把 `STORED` 覆盖成 `FAILED`                                   |
| `fail` 已写下，临时文件还没删，异常还没回到 Celery | `FAILED`，临时文件还在                            | 入口不看 `FAILED`，文件仍在，再次 `add`，已失败的任务可能被改写成 `STORED`                        |
| `fail` 已写下并且文件已删，消息还没确认          | `FAILED`，临时文件不在                            | 入口先判断文件，`fail` 把原来的报错（如「处理超时」）覆盖成「临时文件不存在」                               |
| 第一次执行尚未确认，第二条投递已经开始              | 两个进程同时处于上面的步骤                              | 两次 `add` 各生成一个文档号；或先完成的一方删掉临时文件，后读文件的一方触发 `fail`，把 `STORED` 覆盖成 `FAILED` |


前两个断点再执行一次，结果仍可以收成一条文档。从 `add` 成功到确认之前的断点，会多出文档、把 `STORED` 改成 `FAILED`，或冲掉原本的失败原因。最终方案要挡住的是后面这些断点。

## 3. 方案

重复执行来自「做完再确认」。处理目标是：同一个任务号无论进入 `process_document` 一次还是多次，`documents` 中只有一行，任务进入 `STORED` 或 `FAILED` 后不再被改写。

### 3.1 取走消息时立即确认

把确认提前到执行之前，进程死亡就不会退回消息，第二次执行不会发生。确认之后、写入完成之前进程退出时，MySQL 停在 `PENDING` 或 `STORING`，队列里已经没有这条消息。

该做法把重复换成丢失，与当前「做完再确认」的选择相反。不采用。

### 3.2 进程退出时不退回消息

关闭 `task_reject_on_worker_lost` 后，worker 异常退出的消息被丢弃。效果与提前确认相同：在途任务没有下一次执行机会。不采用。

### 3.3 用租约保证同时只有一个执行者

开始处理前以条件更新把 `PENDING` 抢占为 `STORING`，并记录抢占时间。另一个执行者发现抢占失败就返回。抢占时间超过租约后，允许下一次执行接手，用于覆盖「抢占成功后进程被杀」。

租约能减少两个进程同时写入的窗口，但需要新的时间列，以及「仍在执行」和「执行者已死」的判定。租约过短会让活着的执行者和接手者重叠；过长会让已死亡的任务一直停在 `STORING`。文档号如果仍然每次新生成，接手执行时还是会插入第二行。

幂等写入本身已经能让重叠执行落到同一行。租约不解决文档身份不稳定的问题，这次不引入。

### 3.4 以任务号固定文档身份，并收口终态更新

一条上传任务只对应一份文档，`processing_tasks.id` 与 `documents.id` 都是 32 位十六进制字符串。直接让文档号等于任务号，对象键固定为 `documents/{任务号}/{文件名}`。再次执行写入同一个对象、同一条 `documents` 主键，不会产生第二行。

同时把 `STORED` 和 `FAILED` 作为终态：入口读到终态立即返回；状态更新语句也不再修改终态行，避免并发执行时后结束的一方覆盖先结束的结果。

该方案不改变 Celery 和 Redis 的确认行为，也不增加表字段。

## 4. 最终方案

采用 3.4。队列继续至少投递一次，重复消费在任务函数和数据库写入处收口。

### 4.1 执行规则

`process_document` 按下面的顺序处理同一个任务号：

1. 任务行不存在：返回并确认。
2. 状态已是 `STORED` 或 `FAILED`：返回并确认。不检查临时文件，不调用 `fail`。
3. 临时文件不存在：调用 `fail` 记为「临时文件不存在」，返回并确认。
4. 状态改为 `STORING`（仅当尚未进入终态）。文档号取任务号，对象键为 `documents/{任务号}/{文件名}`。
5. 读取临时文件并写入对象存储与 `documents`。
6. `finish` 写入该文档号，状态变为 `STORED`。
7. 删除临时文件。

过程中抛出异常时：

- 先看任务是否已经由并发执行写成了 `STORED`。若是，删除临时文件并直接返回，不再写 `FAILED`。
- 否则调用 `fail` 记录原因，删除临时文件，再抛出异常。



### 4.2 数据库与对象存储的幂等细节

1. `documents` **插入幂等**：`document_store.add` 接收外部传入的 `document_id`。`document_orm.insert` 使用 `INSERT IGNORE INTO documents ...`。主键已存在时语句正常完成、不抛 `StorageError`，从而不会触发 `add` 里的 `objects.delete` 把另一次执行写好的对象删掉。
2. **终态保护**：`set_status` 和 `fail` 的 `UPDATE` 条件带上 `AND status NOT IN ('STORED', 'FAILED')`。一旦任务进入终态，后续或并发的慢进程无法再把它改回 `STORING`，也无法用新的报错覆盖已有的 `STORED` 或首发失败原因。



### 4.3 再次执行时的结果


| 第一次执行停在                | 再次执行                                                       |
| ---------------------- | ---------------------------------------------------------- |
| 确认之前，尚未写入文档            | 临时文件仍在，按原流程写入，文档号为任务号                                      |
| 对象或文档行已写入，`finish` 未完成 | 对象覆盖同名键，`INSERT IGNORE` 跳过已存在的文档行，随后 `finish`              |
| `STORED`，临时文件已删，消息未确认  | 入口看到 `STORED`，直接返回                                         |
| `FAILED` 已写下，消息未确认     | 入口看到 `FAILED`，直接返回，保留原始失败原因                                |
| 两个进程同时执行，先完成者删掉了临时文件   | 后执行者读文件失败时，因任务已是 `STORED`（且 `fail` 不改写终态），不会把结果改成 `FAILED` |




### 4.4 不包含的范围

- 不调整 `acks_late`、`reject_on_worker_lost`、软超时和硬超时。
- 不增加抢占时间、租约或定时补投。
- 不处理客户端用新的任务号再次上传同一文件。
- 分块和向量化接入后，也要使用这个稳定的文档号继续写入，避免后续步骤再为同一次上传生成第二套数据。
