# 父块共享缓存与按文档修订隔离的布隆快照

状态：已实现缓存与回填服务，聊天流程待接入。关联 [#26](https://github.com/Liyuhnag/rag/issues/26)。

## 背景

多个子块、多个检索请求和多轮对话会命中同一个父块。重复读取正文增加 MySQL 压力；正文缓存又不能让已删除、未 READY 或旧版本的文档继续参与回答。

## 决定

- 正文采用 Redis + MySQL 两层读取，不增加进程内 LRU，不缓存空值。正文无 TTL，由独立实例的明确 `maxmemory` 与 `allkeys-lfu` 管理容量。
- 队列、正文、Bloom/锁分别使用三个独立 Redis 实例，避免正文淘汰锁或布隆位图。guard 使用 `noeviction`；平台提供高可用。
- 使用按父块加锁、拿锁后重查、批量回源、token 安全解锁减少热点重复查询。Redis 故障时以进程共享信号量和超时限制回源压力。
- 调用方必须传入授权后的文档版本范围。正文命中前后仍从 MySQL 校验 READY 与当前文档修订，权限控制不能由缓存 key 代替。
- 缓存及过滤器均包含文档 `parse_version` 与 `updated_at`。只用版本无法隔离同版本重试/重写；现有 chunk 替换事务及 READY 发布都会更新 `updated_at`。未来 chunk 写入也必须遵守这个约定。
- Bloom 使用共享 Redis Bitmap，按文档修订完整构建并一次原子发布，避免全局增量位图的“数据库已新增、位尚未同步”窗口。构建查询也核对修订标识，计数不一致不能发布。初始为空、数据不完整、超限、读取/构建失败时放行。
- 布隆快照设置 24 小时清理期限以回收历史修订；快照过期后重建或放行。该期限不适用于正文，无负缓存控制新增 chunk 的可见性。

## 取舍与边界

缓存命中仍需轻量文档元数据 SQL，优先保证状态正确，减少的是正文查询。首次 Bloom 构建需要 ID 扫描；上限 100,000 个 ID，超限放行，默认误判率目标 1%。并发冷启动可能重复构建，受数据库并发预算限制。

采用按修订快照，避免在本次引入全局布隆重建、水位及可靠增量消息链路。后续规模若需要全局 Bloom，必须另行设计发布及重建协议，不能把缺失位图当成空集合。

进程信号量不等同于跨进程全局限流；所有 worker 的总并发需要结合部署规模配置。Redis 锁不是严格执行一次的保证。同步数据库超时也不是可取消的整条 SQL 硬截止。

chunk 继续使用确定性 UUIDv5。本次不实现未来子块查父块接口、不实现租户 ACL、不在应用中实现 Redis 高可用。

运行参数、接入示例和验证方式见 [父块回填说明](../../backend/services/retrieval/rag/fusion/backfill/README.md)。
